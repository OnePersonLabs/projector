**User need:** The dev agent should act as project owner and consultant, responsible for ensuring mutual understanding rather than merely following a detailed edit request. The user invokes Matt Pocock's “grill-me” skill as an example of the desired interaction. That skill's actual contents were not inspected in the available exchange; no particular protocol is established by this reference.

**Assistant proposal:** A durable **Project Steward** represents the project across model sessions. The model invocation supplies temporary cognition and conversation; it is not the sole repository of project identity or responsibility. This extends the inherited holon distinction between persistent semantic identity and ephemeral model invocation.

The steward would use retained knowledge to ask questions at the **decision/ambiguity frontier**, rather than impose a fixed interrogation. The illustrative question was whether a synthesizer capability belongs intrinsically to every instrument or is an optional advertised capability. That ambiguity changes the architecture, so resolving it has more leverage than asking the user to prescribe files and methods.

The steward then projects its understanding back to the user before execution. This is substantive agreement about what the software should become, not just approval of an opaque patch.

**Status and boundary:** The stewardship relationship is explicit user intent. Durable ownership, frontier-based questioning, and the particular conversational sequence are assistant mechanisms. No autonomous authorization policy was specified. ### ORBIT/C2: Close the gap between semantic change and concrete transformation

**Diagnosis:** Knowing which concepts and requirements are implicated is not the same as knowing exactly what repository operations realize the desired change. The assistant calls this a “missing middle,” while the baseline only establishes incomplete public orchestration, not the absence of every relevant internal mechanism.

**Candidate mechanism:** A **Materialization Compiler**, a provisional name, would connect two levels:

```text
request → semantic change
semantic change + current implementation topology → concrete transformation program
```

The first level identifies meaning, participants, requirements, and architectural decisions. The second determines actual removals, insertions, replacements, moves, and refactorings. Its output is not another prose assignment requiring each worker to rediscover the architecture.

The assistant's illustrative target program includes:

```text
Excise:    LegacySynth, obsolete caller relation, obsolete fixture
Insert:    FmodSynth implementing InstrumentSynthesizer
Replace:   Composer → LegacySynth with Composer → InstrumentSynthesizer
Refactor:  selected symbols while retaining frontend independence
Preserve:  browser fallback behavior and event ordering
Validate:  contract, parity, and dependency-boundary checks
Bind:      reviewed source state and an explicit changed-region envelope
```

These names and operations are examples, not observed repo facts. Their role is to distinguish a concrete target program from “modify this module appropriately.” The user specifically values complete excision of obsolete material as well as construction and refactoring; deletion should not disappear from synthesis into an additive-only feature workflow.

**Expected leverage:** Resolve shared design and targeting once, then give execution machinery bounded work instead of repeated interpretive assignments. This could extend existing plans, capsules, and transforms rather than require an entirely separate subsystem. Neither a full compiler contract nor its completeness was demonstrated.

### ORBIT/C3: Deterministic envelope around nondeterministic synthesis

This is the assistant's main qualification to the orbital image. It explicitly rejects promising that every substantial implementation can be predetermined from a mature proposal.

Instead, creative work would occur before a **mutation barrier**, meaning a boundary between exploratory candidate construction and application to the canonical repository:

```text
semantic contract
→ synthesis in an ephemeral worktree or virtual filesystem
→ candidate implementation
→ analysis of its structural and semantic delta
→ validation
→ freeze exact transformation and bind approval
→ state-checked canonical application
```

A model may still search, write, revise, and test while constructing the candidate. What changes is the authority and status of those writes: they are provisional rather than canonical. The prepared transformation applies to its bound state or refuses application when its basis no longer matches. Existing state-binding and approval machinery motivated this proposal.

**Essential distinction:** Predictable application is not deterministic invention. Nor does freezing a patch establish that it realizes the accepted meaning. The source's equation, `state S + transformation T = state S′`, describes the intended execution relationship, not a proof of semantic correctness.

The claimed benefit is to stop the canonical repo from participating in unresolved design confusion. Scratch-state isolation, freezing, and state-bound execution are candidate means; the thread did not establish that this requires a new representation beyond existing machinery.

**Unresolved:** The reply did not specify recovery from an incomplete impact model, how much work can be retained after invalidation, or the cost of reaching the barrier. Its “coding intelligence has mostly happened already” claim concerns the execution stage, not the total development process.

### ORBIT/C4: Orbital roles, explicit preservation, and bounded refactoring

The user's satellite metaphor carries several distinct requirements: concrete targeting, deliberate removal, outlines of intended structure, coordinated construction, localized refactoring, and validation. It should not be compressed to “use parallel agents.”

The assistant translates the satellites into specialized mechanisms: AST transforms, codemods, symbol movers, structured-data transforms, generators, graph rewrites, migration runners, exact file operations, and validators. Reasoning models handle unresolved semantic work rather than every execution action. A **Transformation IR** is a proposed intermediate representation of operations and dependencies, not an implemented language.

The sketch includes target selectors, semantic purpose, preconditions/postconditions, dependency edges, expected and forbidden touched units, validators, and synthesis provenance. Provenance distinguishes deterministic, generated, model-synthesized, and human-authored work; it does not itself certify correctness.

Two particularly valuable seeds are:

**Preserve alongside change.** A proposed `PreserveOperation` records what must not change. Protection is not limited to untouched files: a public contract, fallback behavior, or event-ordering property may need preservation despite surrounding edits. Its purpose could be served by constraints or completion obligations rather than a literal executable operation.

**Refactor as a bounded problem.** Instead of “make this cleaner,” specify the exact scope, intended zero behavioral delta, permitted structural changes, invariants, and an objective such as reducing coupling or eliminating duplicated responsibility. The example forbids public-contract and persistence-schema changes. This is a desired contract, not an established proof of equivalence.

**Limits of the metaphor:** The user imagines one progressive iterative pass, and the assistant proposes a dependency DAG. The exchange does not establish a universal deletion-first schedule, maximum useful parallelism, or a sufficient validation schedule. These remain design questions; the metaphor is not an executable scheduling algorithm.

## 4. Integration map and unresolved tensions

The common direction is to move responsibility from transient editing instructions into durable understanding and a prepared change contract. The mechanisms remain separable:

- **Existing semantic governance ↔ C1/C2:** Retained meaning may support better consultation and targeting. Existing compiler/planning facilities may subsume some proposed machinery; the earlier inspection does not settle the boundary.
- **Plans, capsules, transactions ↔ C2/C3/C4:** These are plausible implementation foundations. A new IR could clarify targeting or duplicate existing contracts. Ordinary authorized host edits remain a live compatibility question.
- **Inherited holons ↔ C1/C5:** Persistent concern ownership could supply constraints before materialization and reconciliation afterward. This is shared lineage, not independent confirmation of holons' value.
- **Efficiency priority ↔ C3/C6:** More preparation may reduce expensive surprise, but the source provides no threshold for when preparation is worthwhile or ready. The user's desire for precision should not become unbounded planning ceremony.

There is also an unresolved granularity tension between a mature whole proposal, creative scratch-state iteration, and progressive coordinated execution. The source does not choose whole-change freezing versus smaller prepared units. That question must not be silently resolved by treating the most emphatic assistant diagram as an approved specification.

## 5. Synthesis closure

### Core thesis from this thread

Explore development as negotiated project evolution compiled into bounded, verified repository transformations, rather than transient agents improvising design while mutating canonical state. The architectural and economic advantages remain hypotheses.

### Load-bearing insights and distinctions to preserve

The user's explicit ambitions are stewardship, mutual understanding, precise targeting, efficient coordinated change, complete removal where needed, and validation. Preserve the distinctions between semantic intent and materialization, creative synthesis and deterministic application, change obligations and preservation obligations, and durable responsibility and ephemeral model sessions. The assistant's mechanisms are not user-approved requirements.

### Candidate mechanisms, not sacred architecture

Project Steward, frontier-based questioning, Materialization Compiler, Transformation IR, mutation barrier, scratch-state synthesis, specialized satellites, `PreserveOperation`, bounded refactor contracts, and holon composition are replaceable. Their purposes may be absorbed into existing facilities or served differently; no subsystem-per-name interpretation is warranted.

### Questions the final synthesis must resolve

Which capabilities are missing versus already latent in plans/capsules/transforms? What establishes readiness without claiming certainty? How much transformation should be frozen together? How are surprises handled without restarting everything? When does preparation justify its total cost? Does persistent concern ownership materially improve this path? Exact names and representation syntax can wait.

### Relationship to current Projector

The proposed delta is a stewardship-to-materialization workflow built around earlier-observed semantic and transactional foundations, potentially narrowing free-form canonical edits. Verify the baseline and public workflow limits before deciding whether this extends, replaces, or merely exposes existing capabilities.
