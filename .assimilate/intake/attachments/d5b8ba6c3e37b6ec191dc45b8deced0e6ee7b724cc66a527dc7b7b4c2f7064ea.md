# Projector S-model: research checkpoint

Research cutoff: September 10, 2026.
Status: a research proposal, not an implementation specification or a claim of experimental success.

## 1. The decision

Build a complexity-preserving research prototype, not a single-concept demonstration and not a rewrite of Projector. The relevant experimental unit is an evolving, coupled software system. Small component experiments remain useful for debugging the machinery, but their results cannot establish or refute the whole-system thesis.

The target is not an impressive project chatbot. It is a material improvement in the ability of a frontier coding agent to evolve a complex system while preserving its intended identity, rationale, constraints, and legitimate exceptions.

No current Projector repository was inspected for this checkpoint. Its implementation status, drift, and suitability as an integration target remain unassessed. The conversation and attached design excerpts supply the proposal; the sources at the end supply external research. Proposed experimental sizes, interfaces, and acceptance criteria below are recommendations, not prior user decisions.

## 2. The conception to preserve

S denotes the system conception: what the software is, why its distinctions exist, what must remain true, and how its decisions should change when their premises change. S includes more than present requirements or code. Its useful content includes rationale, rejected alternatives, authority, ownership, conditional decisions, exceptions, counterexamples, and unresolved questions.

The proposed lifecycle is:

```text
provenance-bearing observations and decisions
                    |
           semantic reconciliation
                    |
        current conception + useful experience
                    |
     clean construction of a learned project state
                    |
      project counterpart <-> frontier coding agent
                    |
          code and other representations
                    |
      independent checks and new observations
                    |
           proposed evidence events
```

Developer questioning is an active part of the loop. The system should ask scenario-based questions that distinguish materially different conceptions, rather than collect cheap verbal agreement. The question interface can be multiple choice with an escape hatch, but the research problem is selecting consequential questions and preserving the resulting authority and uncertainty.

The learned state is repo-versioned and disposable. Its source evidence is not reconstructed from whatever the model currently believes. A clean rebuild starts from a pinned foundation model and fresh project-specific parameters or memory, not from the last adapted project model. This does not require pretraining a language model from random initialization.

The event log is preserved, but not blindly replayed as a training chronology. The training projection separates the present conception from historical experience that remains decision-relevant. A corrected spelling ordinarily need not become neural memory. A rejected dependency may need its rationale, assumptions, and reconsideration conditions preserved.

The more ambitious horizon is that code and runtime submodels become alternative materializations of the conception. The first serious experiment should retain semantic reconstruction as a test, but need not build a model-native application runtime or generative UI platform.

## 3. The hypothesis, stated without magic

At an explicit resource budget, a persistently learned, project-specific counterpart, rebuilt from reconciled experience, can reduce accumulated semantic drift during a sequence of cross-cutting software changes compared with strong non-parametric approaches given equivalent evidence and developer input.

The strongest version is about learning project-specific consequences, not memorizing more facts:

- Predict distant effects of a proposed change before being given the relevant document fragment.
- Explain why a locally plausible implementation would violate the larger conception.
- Distinguish intentional exceptions from accidental inconsistency.
- Reconsider a former decision when its premises change, without resurrecting unrelated obsolete decisions.
- Guide implementation while leaving exact contracts and checks anchored to inspectable evidence.

An advantage might arise from amortizing project-specific integration over many development acts. It need not arise from language becoming unnecessary. In an MCP/CLI collaboration, the frontier agent still receives messages. The proposed saving is that the project counterpart does the relevant reasoning before communicating a bounded consequence or challenge, rather than repeatedly requiring the frontier agent to reconstruct the whole project.

## 4. Corrections to earlier brainstorming

### Neural state does not guarantee understanding

A learned representation can memorize source wording, learn misleading associations, or omit critical exceptions. Cartridges found that fitting a corpus with next-token prediction did not by itself yield broad question-answering competence; its self-study and context-distillation recipe mattered. [R1]

The claim must be demonstrated through held-out interactions and code effects, not inferred from the presence of an adapter or latent state.

### Event sourcing preserves provenance and recoverability, not truth

An event can faithfully record a wrong claim. A developer decision can be authoritative about product preference without being authoritative about an external technical fact. A code observation can describe an implementation defect rather than a requirement.

Semantic reconciliation therefore needs to preserve distinctions among accepted intent, measured behavior, model inference, proposal, rejected alternative, and unresolved conflict. No successful model-generated patch should automatically become evidence that its inferred rationale was intended.

### Clean rebuilding does not guarantee absence of forgetting or identical behavior

It avoids carrying forward the previous project adapter's optimization history. It does not eliminate interference within the new training run, inadequate sampling, limited capacity, optimization variance, or a faulty curriculum. Byte-identical reconstruction also requires more than a seed; PyTorch explicitly limits reproducibility guarantees across versions and platforms. [R9]

Archive exact accepted artifacts for operational rollback. Evaluate independently rebuilt artifacts for behavioral equivalence rather than assuming it.

### Disagreement does not uniquely diagnose underspecified intent

Independent models can disagree because the evidence is ambiguous, but also because one model failed to learn or reason correctly. Agreement can likewise reflect shared errors. Model disagreement is a probe-selection signal, not a calibrated proof that the developer must decide something.

### Prose is not intrinsically incapable of representing S

The proposal does not need that assertion. The stronger claim is about the efficiency and fidelity of repeatedly using a representation under bounded inference resources. Weights, structured facts, and language are all encodings with different failure modes. A strong symbolic/retrieval baseline may win for exact constraints.

### The entire project cannot be declared reconstructable in advance

Reconstruction must be judged against declared material properties and allowed degrees of freedom. Output source need not match byte for byte. Conversely, a generic app that passes a few acceptance tests is not evidence that the project's conceptual identity was preserved.

## 5. Relevant prior art, checked during this assessment

**Cartridges, June 2025.** Trains reusable per-corpus KV representations using synthetic self-study conversations and context distillation. It explicitly targets broad queries and structural awareness, rather than mere memorization. Reported benchmark gains establish an adjacent mechanism, not software-evolution reliability. Training cost is material. [R1]

**Doc-to-LoRA, February 2026.** Meta-learns a hypernetwork that generates a context-specific LoRA adapter, enabling later questions without re-consuming the source context. It is close to the proposed context-to-learned-state boundary. The paper reports limitations including a gap to in-context learning and expensive target-model-specific meta-training. [R2]

**Doc-to-Atom, June 2026.** Compiles semantically typed atoms into small adapters with provenance keys and query-conditioned composition. It substantially overlaps the notions of a semantic compiler, modular learned memory, and supported retrieval. Its evaluations concern QA, and the authors report limitations in decomposition and performance relative to in-context learning. Its atomization strategy should not be adopted uncritically: Projector must test whether cross-atom relationships survive. [R3]

**Dual-Layer Agentic Memory, August 23, 2026.** Studies selective external memory admission and periodic consolidation into model parameters. This is relevant to the distinction between raw experience and useful learned memory. It does not establish the proposed clean-rebuilt, event-sourced software-conception lifecycle. [R4]

**HippoRAG 2, February 2025.** A strong non-parametric counterexample to treating retrieval as nothing more than nearest-neighbor chunks. It studies graph-mediated factual, associative, and sense-making memory. A credible Projector experiment needs such strong families of alternatives, not a weak top-k retrieval strawman. [R5]

**SWE-EVO, December 2025.** Evaluates multi-file software evolution rather than only isolated issue resolution. It reports a substantial gap between its harder evolution tasks and single-issue benchmark results for the tested system. This supports measuring coupled change, but not a current claim about every model or a proof of Projector's diagnosis. [R6]

**SWE-Bench-CL, 2025.** Organizes coding issues chronologically to study accumulated experience, transfer, and forgetting. Longitudinal evaluation itself therefore also has prior art. [R7]

**Self-Guided Test-Time Training, July 2026.** Reports that the quality of the context spans selected for adaptation can make the difference between improvement and degradation. It reinforces treating the curriculum as a research variable. [R8]

Assessment: the individual neural-memory premise is not new. The particular integrated lifecycle and its usefulness for preserving software conception remain legitimate research targets. This was a focused prior-art review, not an exhaustive novelty search.

## 6. The minimum discriminating world

The prototype must be inexpensive in operational infrastructure without being impoverished in conceptual interactions.

A starting design could contain 30-80 meaningful concepts, overlapping constraints and exceptions, several histories of architectural change, and 50-200 substantive evolution tasks. These are planning ranges, not scientifically established thresholds. Calibrate the actual difficulty using pilot runs across representation types before locking the scored suite.

A music-platform research environment is suitable because it can couple identity, persistent skill, game state, sessions, evidence, assessment, multiplayer authority, offline operation, clock domains, audio scheduling, plugins, privacy, and migrations. It is not a reduced specification for Psychord. It is an evaluation environment designed to reproduce the relevant engineering pressures.

A task such as allowing an offline guest session to join a multiplayer room can require coordinated reasoning about identity reconciliation, evidence deduplication, provisional feedback, assessment authority, clock conversion, and privacy. Every local change can look plausible while the global result is wrong.

The important difficulty variables are not just lines of code or document length. They include the number of independent constraints that jointly govern a change, the distance between their evidence, exception depth, premise changes, and accumulated decision history.

Do not manufacture failure by padding documents, hiding legitimate evidence from controls, or giving only the S-model the answer. Include low-coupling regimes too. The goal is to observe where and why performance separates, not to design a theatrical collapse.

Use deterministic service doubles and simulated clocks where they preserve the property under test. A simulation cannot substantiate actual browser audio latency, real-device reliability, or cloud production behavior; those require later measurements in the relevant environment.

## 7. Five discriminating tests

### A. Distant consequences without a retrieval hint

Supply an ordinary feature request. Require discovery of its cross-cutting implications before providing package names or relevant rule IDs. Score both missed consequences and invented ones.

The intended problem is not merely finding an answer after being told where it lives.

### B. Same present state, different reasons

Create two project worlds with the same current backend choice but different reasons for choosing it. Change one premise. The correct architectural recommendation should change in only the world where that premise was load-bearing.

This tests learning the decision function rather than the label of the current choice. All arms receive the rationale evidence. The distinguishing scenarios and expected consequences stay out of training.

### C. Selective historical retention

Include incidental renames, substantive rejected alternatives, scoped exceptions, and migrations in progress. Later test whether obsolete trivia is ignored while useful conditional rationale is retained.

Add a controlled variant where an old typo became a public identifier used by external clients. In that world the rename history is material. Historical value depends on consequences, not on a fixed category such as "rename events are noise."

### D. Developer disambiguation

Include genuinely underdetermined changes. Score whether the system asks a question that distinguishes materially different valid architectures, recognizes when existing evidence already resolves the issue, and incorporates the answer without excessive questioning.

Use a consistent answer oracle or recorded human adjudication. Give all arms the same access to developer answers, and charge the associated interaction cost.

### E. Reconstruction after evolution

Hide a substantial implementation region after many changes. Reconstruct it from the available representation and external contracts. Judge behavior, ownership, architectural boundaries, migrations, temporal properties, and declared freedom of implementation.

Hide the original implementation from every retrieval path, cache, and tool during this trial. Keep it outside the agent's accessible worktree. Use held-out variations and changed requirements to distinguish reconstruction from memorized source recovery.

## 8. Baselines that can actually refute the neural claim

The strongest comparison gives both sides equivalent accepted evidence, rationale, developer judgments, and exact artifacts. The experiment varies how that knowledge is integrated and used.

| Arm | Project knowledge mechanism | What the comparison diagnoses |
|---|---|---|
| A | Strong code/spec-driven harness with history-aware and structured retrieval | Practical improvement over competent existing development |
| B | The same reconciled current-state and rationale curriculum, used through explicit structures and retrieval | Whether semantic curation alone explains the gain |
| C | The same local foundation model acting as a counterpart through retrieval, without project training | Whether merely adding a second reasoning agent explains the gain |
| D | A project-trained counterpart, otherwise matched to C | The incremental value of learned project state |

Use additional diagnostic ablations rather than declaring every variation a product component. Examples are a learned counterpart without raw-document access, a current-state-only curriculum, omission of historical rationale, and an intentionally stale project adapter.

Also give a diagnostic agent the correct relevant evidence explicitly. This is not a deployable retrieval baseline; it separates evidence-selection failure from reasoning failure. Do not assume it is a literal mathematical upper bound.

Compare frontier-token budgets and total amortized cost separately. Dataset generation, local inference, rebuilds, retrieval, wall-clock delays, and human correction are not free. A method may be valuable at one operating point without dominating every resource regime.

## 9. Evaluation must remain outside the learning loop

Keep the authoritative acceptance model and hidden scenario suite outside the agents' writable scope. Every legitimate requirement must nevertheless have supporting evidence available to all arms. Hidden evaluation cases must test consequences, not secret requirements.

Use executable behavioral and temporal checks, structural boundary checks, controlled counterfactuals, and blinded human adjudication for irreducibly semantic judgments. Model reviewers can assist but should not be the sole authors, trainees, and judges of the same claims.

Hold out combinations of principles and classes of changes, not merely paraphrases of training examples. Where possible, hold out a whole project world. Separate corpus creation, training examples, evaluation generation, and adjudication sufficiently to detect answer leakage and correlated mistakes.

Run two modes:

- Matched clean checkpoints to diagnose understanding and implementation ability under comparable starting conditions.
- Continuous independent branches, each carrying its own accumulated code changes and mistakes, to measure actual drift over time.

Repeat trajectories with different starting conditions or seeds. Report uncertainty at the trajectory/project level, not as if hundreds of correlated questions were independent evidence.

## 10. Outcomes that matter

Track a severity-weighted divergence measure against the current accepted conception, but also report its components. A single aggregate can hide unacceptable failures.

Important components include constraint and ownership violations, missed distant consequences, unsupported invented rules, correct handling of exceptions, preservation of revision semantics, inappropriate resurrection of rejected alternatives, false-positive blocking of valid changes, developer repair effort, and reconstruction fidelity.

Evaluate both the number of completed changes and the quality of retained behavior. An agent that refuses everything must not win by never introducing drift.

Plot divergence and cost across change horizon, coupling difficulty, and context budget. The meaningful result is a materially better quality-cost tradeoff that persists in the high-coupling regime and transfers beyond one hand-designed world.

Predeclare the minimum practically worthwhile effect after a non-scored pilot, then freeze it before the main run. Avoid inventing a universal pass percentage unsupported by the application's tolerance for errors.

## 11. Training and runtime boundaries worth protecting

Use a pinned base model and recreate the project-specific learned artifact at accepted semantic revisions. Start with established adapter or learned-memory methods before contemplating a new hypernetwork architecture. Published methods establish that such mechanisms can exist; they do not establish that the complete proposed workload fits any particular local hardware or cost envelope.

Train for consequences, contrasts, scoped exceptions, revision behavior, and appropriate uncertainty, not just prose continuation or project trivia. Current-state examples and historical examples should clearly distinguish current authority from past rejection. A final historical training stage must not silently overwrite present-state competence. Whether to interleave or stage the curriculum is an empirical variable.

The compiler is part of the risk, not an oracle. It can experience the same fragmented-context problem as the coding agent. Offline time permits multiple passes and explicit coverage checks; it does not create missing information. Preserve source links, unresolved conflicts, and gaps rather than silently filling them with plausible narrative.

A model artifact should be pinned to an event revision and curriculum recipe. A counterpart must report when it is stale relative to current accepted intent. Newly accepted exact rules should remain immediately accessible while a replacement model is built; do not rely on a stale weight state to override them.

Expose a small collaboration contract: orient a task, identify consequences, challenge a proposal, request material clarification, and review actual changes. Tool outputs should distinguish accepted constraints, inferred consequences, uncertain claims, and supporting evidence. Numeric confidence requires calibration rather than invented precision.

The local model need not be the sole permission authority. The learned part can propose and generalize; exact checks and explicit acceptance boundaries remain independently inspectable. This is compatible with model-driven development because the distinction concerns enforcement reliability, not whether Markdown becomes the canonical mind again.

## 12. What would change the research direction

If the trained counterpart beats weak code-only controls but not the same curriculum with structured retrieval, the evidence favors the curriculum or knowledge organization rather than neural storage.

If it answers questions well but does not improve code evolution, the interaction protocol or implementation reasoning is the bottleneck.

If it works on snapshots but becomes stale or expensive under updates, rebuild economics and revision handling are the bottleneck.

If it succeeds only on near-training examples, it has not demonstrated the proposed transferable conception.

If full relevant evidence does not enable the frontier agent to reason correctly, the problem includes reasoning capacity, not just memory selection.

If several reasonable neural implementations fail within the declared resource envelope while a non-parametric counterpart succeeds, stop treating the neural representation as necessary for that envelope. This is a bounded conclusion, not a universal disproof of future learned-state methods.

## 13. Recommended next artifact

Construct the difficult evaluation world and the end-to-end experimental harness together, with the source evidence, initial runnable implementation, accepted constraints, scoped exceptions, revision history, and a protected evolution suite.

It must be a real coupled organism, not a single-feature demo. It need not be polished or integrated into production Projector. Component smoke tests are necessary engineering checks, but the investment decision belongs to the whole-system result.

The research commitment is to preserving and using project conception under change. The neural representation is a serious candidate mechanism, not a conclusion that the experiment must protect.
