# Coupled-evolution experiment

`§coupled-evolution` · Test whether persistent understanding improves repeated valid changes at comparable total cost.

## The central question

Does a project-specific learned counterpart provide an advantage beyond the same curated knowledge, tools, context interface, and ordinary retrieval?

A successful demonstration must preserve meaningful coupling and accumulated change. A one-concept toy, a single impressive answer, or a benchmark that replaces the agent's code with a clean reference between steps cannot establish the intended benefit.

## Experimental world

Use a bounded but interrelated application. An illustrative music system can include persistent skill identity, sessions, evidence, multiplayer authority, offline participation, device identity, audio-clock responsibilities, privacy, plugins, and migrations.

Infrastructure may be simulated to reduce implementation cost, but preserve the relevant relationships. A simulated audio subsystem can test ownership and scheduling semantics; it cannot establish production-grade audio latency.

The world should be understandable enough for independent adjudication and rich enough that one change has non-obvious consequences elsewhere.

## A sequence that actually tests understanding

Start from accepted behavior and obligations, then evolve the system through connected changes. For example, introduce offline participation, allow a guest to join an existing account, reconcile observations, revise assessment authority, and add a consumer after a migration has been planned.

A useful task is: **an offline guest joins a live room without interrupting playback**. Correct handling can involve identity, deduplication, provisional feedback, canonical authority, clocks, privacy, and synchronization together.

Do not name every relevant rule in the task. Hold out combinations that require discovering interactions, not simply recalling a supplied checklist.

## Discriminating probes

| Probe | What it distinguishes |
|---|---|
| Same current architecture, different historical rationale | Current-state pattern matching versus conditional understanding. |
| A governing premise reverses | Appropriate revision versus defending stale conclusions. |
| Names change, obligations do not | Surface robustness. |
| Names remain, authority changes | Sensitivity to meaningful differences. |
| A fourth consumer appears after planning | Query-membership freshness versus edited-file-only checks. |
| A valid improvement violates a superficial pattern | Real obligations versus false-positive policing. |
| Relevant source is removed in a disposable reconstruction test | Learned or retained understanding versus hidden source access. |
| Context resets midway | Durable state and disclosure behavior versus accidental session memory. |

Include favorable and unfavorable cases for every approach. A system that refuses every difficult change can have few violations and still be useless.

## Baselines

Use a competent frontier-only owner with source, documentation, and history-aware retrieval. Add an explicit-knowledge condition receiving the same reconciled curriculum through structured records and retrieval. Add a generic local counterpart with the same collaboration tools but no project-specific training. Compare with the trained counterpart under otherwise matched conditions.

These comparisons isolate different mechanisms. If the explicit curriculum produces the gain, curation may matter more than training. If the generic counterpart performs similarly, division of work or tooling may explain the gain. If neither helps, the persistent-counterpart hypothesis is weakened for that workload.

Do not give the trained condition private human decisions while handicapping the retrieval baseline with raw, contradictory transcripts.

## Factor the collaboration interface

A complementary two-by-two comparison crosses generic versus project-trained counterpart with compiled-context versus shared-intervention collaboration. Include the frontier-only baseline and vary communication budget.

This distinguishes learned project judgment from an improved interface. It also tests whether useful reasoning remains local rather than being transferred to the frontier as another large context dump.

## Keep the trajectory intact

Carry each condition's own accepted implementation forward. Measure after every checkpoint and across the full sequence. Clean-checkpoint restarts can be useful diagnostic experiments, but should not replace the longitudinal test.

The acceptance basis evolves with authorized changes. Do not score a legitimate new requirement as a violation of an obsolete rule. Maintain a versioned record of what applied at each checkpoint.

## Outcomes and full costs

Primary outcomes include accepted valid changes, preservation of applicable obligations, correct handling of authorized revisions, missed cross-concept effects, unnecessary objections, and repair needed before integration.

Track total cost: curriculum curation, training, local inference, frontier inference, tools, context preparation, verification, integration, human clarification, and later attributable repair. Report latency and usage separately when there is no defensible conversion.

Observe the quality trajectory, not only final pass rate. Structural growth, duplicate ownership, migration residue, and accumulating test assumptions can matter even when functionality remains green.

## Independence and validity

Keep held-out scenarios and acceptance obligations independent of the candidate being tested. Use deterministic oracles where available, inspectable traces, and blinded human adjudication for meaningful ambiguity.

A model should not create its own curriculum, infer the answers, grade the answers, and thereby certify understanding. Model judges require calibration and error analysis. Preserve failure cases, ambiguous judgments, and denominator information.

Prevent leakage during reconstruction by removing source access from retrieval, tool caches, prior context, and hidden artifacts in the experimental condition. Do not remove the user's real repository.

## Decision rules

Support for the hypothesis requires repeated, meaningful improvement that survives fair baselines and full-cost accounting. A local improvement on one metric may still be a tradeoff rather than an overall gain.

A null result is useful when it identifies which mechanism was unnecessary. A trained model that improves explanation fluency but not consequences, a context compiler that hides obligations, or a scheduler that accelerates generation while blocking verification should not be promoted on appearance.

The minimum viable experiment preserves causal coupling. It does not need production scale, a finished Projector implementation, or a new orchestration framework.
