# Decision frontier

The core design is coherent enough to navigate, but several choices remain genuinely open. These are specific decisions, not a generic task list. Illustrative options are not implementation commitments.

## Persistent representation

**Question:** Does project-specific training improve consequences and authorized change handling beyond the same knowledge in explicit records and strong retrieval?

**Alternatives:** explicit concept system; generic local counterpart; learned project checkpoint; hybrid.

**Decision-changing evidence:** the matched, repeated [coupled-evolution experiment](../experiments/coupled-evolution.md), including training and curation costs.

**Until settled:** keep evidence and exact obligations inspectable outside weights. Do not require a learned counterpart for the useful non-neural components.

## Conception authority and promotion

**Question:** Which changes may assimilation accept automatically, which remain proposals, and which require a developer decision?

**Material distinction:** incorporating a duplicate definition is different from resolving a disputed requirement or authorizing repository edits.

**Needed decision:** a small promotion policy based on consequence and authority, with a route for unresolved alternatives. The archive does not establish a final policy.

## Persistent workspace boundaries

**Question:** Is there one repository-wide assimilation space, multiple subject spaces, or a combination with explicit cross-space references?

**Related questions:** which raw inputs remain durable; where temporary campaigns live; how an existing workspace is located when no new files are supplied; whether a synthesis chat remains useful or becomes optional.

**Until settled:** separate durable conception from disposable execution state. Avoid requiring one giant context or one giant specification.

## Learning updates and freshness

**Question:** When is a delta sufficient, when is incremental learning useful, and when should a clean project-state rebuild occur?

**Decision-changing evidence:** stale-premise probes, cross-branch reconciliation, update cost, forgetting, and repeated-change fidelity.

**Until settled:** tie learned checkpoints and derived artifacts to known bases. Do not mistake exposure to an update for demonstrated integration.

## Context rendering

**Question:** Which views, disclosure triggers, and incremental supplements improve outcomes for actual receiving models?

**Open mechanism:** a simple Markdown index may suffice before a query service, adaptive renderer, or concept resolver is justified.

**Evaluation:** compare against competent retrieval; include omitted obligations, context resets, and changed revisions. Keep concept truth separate from delivery optimization.

## Routing and spending authority

**Question:** Should the selected model authorize only that family, or also explicitly qualified cheaper alternatives? How should the user opt into an exceptional stronger route?

**Current proposal:** session-relative defaults, no silent more-expensive model, supported per-task effort changes, deterministic fast paths, and bounded work. See [session-relative routing](../orchestration/session-relative-routing.md).

**Unverified implementation details:** actual installed Codex version, available model/effort combinations, native child controls, inherited role overrides, and whether all launch paths can be constrained.

A configuration or instruction is not evidence that a hard spending boundary is enforced.

## Materialization coverage

**Question:** Which languages and operation families can supply precise targets and sufficiently complete dependency evidence?

**Alternatives:** typed refactoring tools, syntax transformations, generators, constrained model synthesis, or combinations.

**First discriminator:** a cross-package replacement with dynamic registration and an introduced consumer. Do not claim whole-system semantic completeness from precise edits alone.

## Experimental scope

**Question:** Which minimum world retains the interacting obligations without becoming an expensive product build?

The music-system example is an experimental vehicle, not a claim about existing implementation. Simulated infrastructure must preserve causal semantics while avoiding unsupported performance conclusions.

## Phlatland presentation

**Question:** Which client and rendering technology best supports live, grounded project lenses?

A2UI-like and MCP Apps-like approaches remain presentation candidates. The first useful evidence is whether users can answer real project questions correctly and quickly, not a protocol comparison alone.

## Model-native runtime

**Question:** Is there any region where model-mediated execution beats deterministic code after reliability, latency, and controllability are accounted for?

**Disposition:** deferred research branch, not a dependency of the initial system.
