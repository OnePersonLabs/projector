## Verdict

**Yes, there is a real missing piece worth finishing. But the answer is not to bolt a separate SDD system onto Projector.**

The right architecture is:

> **PDD is the whole development control loop. SDD is its native forward-change protocol.**

```text
SDD:
intent → specification → plan → implementation → verification

PDD:
intent → specification → architecture decisions → projections
     → implementation → observation → reconciliation
     → invalidation → retained learning
```

So SDD has not become irrelevant. It has become a **proper subset of Projection-Driven Development**. Projector should provide a complete, excellent default SDD experience—but its specifications, plans, and task documents should be projections of the semantic system, not a second source of truth.

## 1. `projector-lean-delivery` is an internal delivery skill

`.agents/skills/projector-lean-delivery` is a repository-local skill for **finishing Projector itself efficiently**. It is not a product-facing Projector workflow.

It optimizes for:

- one continuity implementer and one continuity reviewer;
- compact 2–5 KB task capsules;
- subsystem-sized vertical slices;
- focused tests during implementation;
- one full gate at the end;
- one comprehensive review and one consolidated repair pass;
- durable worktree/DAG/test context instead of repeatedly reconstructing context. citeturn827402view0turn827402view1turn827402view2

That was a sane reaction to Superpowers/GSD token incineration. It should remain as an **internal Projector maintainer profile**, perhaps eventually renamed something like:

```text
projector-maintainer-delivery
```

It is not the missing SDD apparatus.

So the plugin is the delivery surface on which the missing SDD workflow should be exposed.

# How much SDD is already covered?

A lot.

## Canonical semantics

The current spec defines first-class Requirements and Behavioral Scenarios with stable identities, scopes, origins, evidence, lineage, and many-to-many relations. It explicitly avoids creating them for trivial work where durable identity adds no value. citeturn872728view2

## Intent and relevance

It separates:

```text
WHAT / WHY
WHERE / WHAT-ELSE
HOW
```

and requires semantic identity resolution plus a bounded, inspectable Relevance Closure before committing a semantic delta. citeturn616651view1

## Architecture

It performs architecture preflight only when concerns become material and prevents solution technologies from being smuggled into user intent. citeturn616651view5turn616651view6

## Specification representations

It already models human prose, Gherkin behavior specifications, compact agent context, and machine invariants as generated representations of canonical meaning. Gherkin `.feature` files are explicitly derivative rather than canonical behavior. citeturn872728view0turn872728view1

## Planning and execution

It has state-bound plans, execution capsules, work packets, single-writer coordination, crash-consistent journals, receipts, and change certificates. Every applied plan—including partial or failed plans—is required to emit a certificate. citeturn872728view3turn872728view4

So Projector does **not** need:

- another requirements ontology;
- another Gherkin truth store;
- a mandatory `requirements.md → design.md → tasks.md` chain;
- another phase planner;
- a second approval model;
- another execution DAG model.

Those would duplicate what it already has.

# What is genuinely missing

The missing element is a **persistent, coherent developer-facing change lifecycle**.

The spec has `SemanticChange`, but a Semantic Change is a compiled state-bound delta. It is not quite the durable coordination identity for everything that happens from the first fuzzy request through clarification, revision, execution, failure, resumption, and closure.

## Add one aggregate: `ChangeCase`

```ts
interface ChangeCase {
  id: EntityId;
  title: string;
  status:
    | "captured"
    | "clarifying"
    | "specified"
    | "decision-blocked"
    | "ready"
    | "executing"
    | "verifying"
    | "complete"
    | "partial"
    | "abandoned"
    | "superseded";

  originRefs: IntentOriginRef[];

  intentAnalysisRevisionIds: EntityId[];
  relevanceClosureRevisionIds: EntityId[];

  requirementIds: EntityId[];
  behavioralScenarioIds: EntityId[];
  constraintIds: EntityId[];
  nonGoals: string[];

  architectureConcernIds: EntityId[];
  decisionIds: EntityId[];
  deferralIds: EntityId[];

  semanticChangeRevisionIds: EntityId[];
  specProjectionIds: EntityId[];

  planIds: EntityId[];
  workPacketIds: EntityId[];

  reviewIds: EntityId[];
  approvalIds: EntityId[];

  receiptIds: EntityId[];
  certificateIds: EntityId[];

  continuation?: ContinuationRef;
  currentStateBinding: StateBinding;
}
```

This does **not** become another authority plane. It is a coordination root that references the canonical entities Projector already owns.

The relationship is:

```text
Change Case
    ├─ origin request(s)
    ├─ intent/relevance revisions
    ├─ requirements and scenarios
    ├─ architecture decisions
    ├─ one or more Semantic Change revisions
    ├─ generated spec projections
    ├─ plans and packets
    ├─ reviews and approvals
    └─ receipt/certificate
```

# The spec should be a projection of the Change Case

This is the decisive anti-bureaucracy rule:

> **Projector’s SDD specification is a state-bound representation of a Change Case and its referenced semantic entities. It is not a parallel source of truth.**

From the same Change Case, Projector can render:

```text
human concise spec
technical detailed spec
Gherkin feature
agent compact context
machine predicate bundle
GitHub issue checklist
PR description
OpenSpec-compatible export
Spec Kit-compatible export
GSD-compatible task/phase view
```

The current representation machinery already supports the important semantic-preservation model. The missing work is primarily to scope it around one persistent Change Case and expose it through a coherent workflow. citeturn399879view5turn872728view0

Human edits to a rendered spec should become **proposed semantic deltas**, not silent edits to a second truth store.

# Default Projector SDD flow

```text
natural-language request / issue / PRD / observed delta
                         ↓
                    Change Case
                         ↓
          intent analysis + relevance scouting
                         ↓
             identity resolution against
       existing requirements / scenarios / concepts
                         ↓
            clarification + decision frontier
                         ↓
       requirement / scenario / constraint delta
                         ↓
              architecture preflight
                         ↓
             reviewable spec projection
                         ↓
                    approval
                         ↓
      impact closure + state-bound execution plan
                         ↓
       deterministic work + bounded agent packets
                         ↓
       independent validation + reconciliation
                         ↓
          certificate + retained semantic learning
```

## Process depth should be materiality-derived

Not every change should be forced through all visible steps.

| Profile | Behavior |
|---|---|
| **Quick** | Resolve intent, calculate impact, execute deterministic/bounded work, verify |
| **Standard** | Requirements/scenarios, architecture preflight, reviewable spec, plan, execute |
| **Deep** | Fresh research, contested decisions, adversarial review, staged execution |
| **Migration** | Compatibility strategy, checkpoints, dual-running/cutover/cleanup |
| **Salvage** | Infer intent and patterns from existing reality, then normalize and govern |

These are views over the same transaction engine, not separate workflows.

# Product surface I would add

The low-level CLI could become:

```bash
projector change open "<natural-language request>"
projector change show change:<id>
projector change clarify change:<id>
projector change resolve change:<id>
projector change render change:<id> --profile human-technical
projector change render change:<id> --profile behavior-gherkin
projector change approve change:<id>
projector change plan change:<id>
projector change execute change:<id>
projector change review change:<id>
projector change resume change:<id>
projector change close change:<id>
```

Most users should not need to type that sequence. The Codex plugin should expose a new default skill—perhaps `projector-develop` or `projector-change-case`—that orchestrates it conversationally.

The existing `projector-change` skill then becomes the lower-level **execute an approved change** skill.

That gives a clean separation:

```text
projector-develop
  capture → clarify → specify → decide → approve → execute → close

projector-change
  execute an already approved, state-bound plan

projector-review
  independently challenge evidence and completion
```

# Final judgment

You are not trying to implement SDD because Projector failed to transcend it.

You are recognizing that:

> **Projector already contains nearly all the machinery of an advanced SDD system, but currently exposes it as separate semantic subsystems and a narrow proof-of-concept change path rather than one complete default development experience.**

So the correct next expansion is neither:

```text
add GSD inside Projector
```

nor:

```text
declare SDD obsolete and ignore the unfinished UX
```

It is:

> **Complete Projector-native SDD by introducing a persistent Change Case, making specifications state-bound projections, generalizing the change compiler’s public path beyond the mandatory fixture, and exposing the whole lifecycle through the existing plugin.**

That is a relatively thin product layer over a lot of machinery that already exists. It finishes the job without inheriting the phase-document bureaucracy that burned your quota in the first place.
