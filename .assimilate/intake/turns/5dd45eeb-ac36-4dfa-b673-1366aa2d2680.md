## Assistant

Very definitely. There is substantial overlap, but I’d classify Projector as **adjacent to / partially superseding spec-driven development rather than another SDD tool**.

The overlap is real because both care about this chain:

```text
intent
→ explicit decisions/requirements
→ implementation plan
→ code
→ verification
```

Projector adds a much larger reverse and maintenance loop:

```text
                    ┌─────────────── observe reality ───────────────┐
                    ↓                                               │
intent → decisions → rules/lenses → projections → implementation ──┘
                    ↑                    ↓
                 rationale          reconciliation
                    ↑                    ↓
               live research ← invalidation / changed assumptions
```

### Where it overlaps SDD

Typical spec-driven-development systems want some combination of:

- requirements/spec artifacts;
- architecture/design decisions;
- task decomposition;
- implementation from specs;
- validation that implementation matches the specification;
- persistent project knowledge for coding agents.

Projector absolutely does all of those things.

In fact, things like:

```text
Concepts
Behaviors
Architectural Decisions
Invariants
Semantic Changes
Execution Plans
Completion Contracts
```

are recognizably in SDD territory.

### The critical difference

Most SDD approaches roughly assume:

> **Specification is upstream truth.**

Projector's model is closer to:

> **Intent is upstream authority, but knowledge of the system is continuously reconstructed from intent + decisions + implementation + history + tests + external reality + current evidence.**

That produces several differences.

| Typical SDD | Projector |
|---|---|
| Start by writing a spec | Can start with a messy existing repository |
| Spec → implementation | Bidirectional conceptual ↔ implementation reconciliation |
| Specs mainly describe desired features | Models concepts, rules, architecture, manifestations, decisions, evidence, external surfaces |
| Usually task/project scoped | Persistent semantic control plane |
| Detect deviation mainly through tests/review | Explicit divergence model |
| New feature → new spec | New feature → discover newly material concerns → re-evaluate affected architecture decisions → then plan |
| Files/tasks are primary work units | Semantic changes + projection units |
| Agent gets relevant spec context | Agent gets compiled contextual rules + exact semantic/write scope |
| Refactor impact often rediscovered | Typed semantic dependency/invalidation graph |
| Architecture guidance largely prose | Decisions compile into rules, validators, transforms, impact rules |
| Usually forward-generation oriented | Can normalize arbitrary agent-written code afterward |
| Repository is main target | Repo + CI + infra + cloud + stores + runtime/external surfaces |

That last cluster is the big distinction.

## I think SDD should actually become an explicit conceptual neighbor in Projector

There is a useful way to view the relationship:

```text
                      Software Evolution Control Plane
                                  │
                 ┌────────────────┴────────────────┐
                 │                                 │
         Specification side                 Reality side
                 │                                 │
        requirements / intent               code / tests / CI
        architecture decisions              infra / runtime
        invariants / contracts              external surfaces
                 │                                 │
                 └────────── Projector ────────────┘
```

A traditional SDD system heavily occupies the **left half**.

Projector's differentiator is closing the entire loop.

So I would **not distance Projector rhetorically from SDD**. There's leverage in saying:

> Projector includes the useful parts of spec-driven development, but removes the assumption that humans must completely specify the system up front or remember to keep the specification synchronized.

And there's an even sharper formulation:

> **SDD compiles specifications into software. Projection-Driven Development continuously compiles intent into software *and software back into an accountable semantic model*.**

That is a real categorical difference.

### There is also an interesting potential integration

An existing SDD artifact could simply be another **authored semantic input adapter**:

```text
OpenSpec / Spec Kit / Kiro spec / custom PRD
                  ↓
          Projector semantic model
                  ↓
    concepts / decisions / behaviors
                  ↓
       projections + reconciliation
```

Projector doesn't necessarily need to reinvent every UX convention from the SDD ecosystem.

It could ingest their artifacts and add the part they're generally missing:

**persistent architectural authority + semantic impact + contextual governance + incremental invalidation + reality reconciliation.**

So yes: enough overlap that **we should eventually do a deliberate competitive/adjacency analysis of the SDD ecosystem**. It may reveal pieces Projector should steal wholesale, things it should integrate rather than rebuild, and—more importantly—which portions are genuinely differentiating versus merely our implementation of features that already have mature solutions.
