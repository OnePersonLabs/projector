Everything else is downstream.

## I think the hidden failure is conservation

A software project contains far more than code.

There is some latent object \(S\), call it the **system conception**:

\[
S =
\{
intent,
constraints,
architecture,
semantics,
patterns,
boundaries,
assumptions,
tradeoffs,
history,
known-non-goals,
local conventions,
dependency topology,
quality model
\}
\]

The repository is only a lossy projection of \(S\).

Humans maintain a surprising amount of \(S\) implicitly.

An agent gets a partial reconstruction:

\[
\hat{S}_t = f(\text{files retrieved},\text{prompt},\text{docs},\text{history})
\]

Then modifies the repo using \(\hat{S}_t\).

The nasty part is that **each successful-looking modification can make the repository less capable of reconstructing the original \(S\)**.

So:

\[
S \rightarrow R_0 \rightarrow R_1 \rightarrow R_2 \rightarrow \ldots
\]

while the agent repeatedly estimates:

\[
R_t \rightarrow \hat{S}_t
\]

That is an iterated lossy codec.

Entropy compounds.

And almost every anti-slop technique merely improves one of those reconstruction passes.

That would explain the experience you've been having almost perfectly.

# The solution probably isn't another guardrail

It is a **system whose primary job is conserving software meaning under transformation**.

Code generation becomes almost secondary.

I think Projector has been wandering toward exactly this object, but I'd push it considerably further.

Something like:

## **Software Semantic Control System**

Not "instructions for the agent."

Not "project memory."

Not "architecture documentation."

An actual control plane over development.

It would maintain several distinct representations of the system simultaneously.

### 1. Intent plane

What must remain true?

Not implementation instructions.

Actual invariants:

```text
User skill state is independent of game state.
Games consume capability models but cannot redefine them.
Audio timing may not depend on UI render timing.
Platform integrations may not leak into domain logic.
```

Some machine-checkable. Some semantic.

---

### 2. Concept plane

The canonical decomposition of the thing.

```text
Identity
Skill Model
Instrument
Session
Game
Transport
Audio Engine
Assessment
```

With explicit relationships.

This answers:

> "What objects does this universe contain?"

Most codebases never formally encode this.

---

### 3. Pattern plane

How concepts are permitted to materialize.

Projector already touches this.

```text
Concept:
    realtime-session

Allowed implementations:
    transport adapter
    state coordinator
    reconciliation strategy

Forbidden:
    game-specific state inside transport
    UI-owned authoritative state
```

Now architecture isn't merely descriptive.

It's generative and restrictive.

---

### 4. Implementation shadow

A continuously reconstructed graph of what **actually exists**.

Not what AGENTS.md claims exists.

```text
Concept → modules
Invariant → enforcement sites
Pattern → implementations
API → callers
State → owners
Boundary → crossings
```

Now you can calculate something extraordinarily useful:

\[
\Delta = \text{Declared System} - \text{Observed System}
\]

That's architectural divergence.

Not lint errors.

**Meaning drift.**

---

### 5. Evidence plane

Every architectural assertion gets provenance.

Why do we believe:

> skill state must be game-independent?

Because:

```text
decision: ADR-014
spec: psychord-platform.md §4.2
tests: skill-state-boundary/*
implementation evidence: packages/core-skill/*
```

Agents stop treating every file as equally authoritative.

This alone fixes a startling amount of agent stupidity.

---

### 6. Change-impact model

Before modifying anything, derive the semantic blast radius.

Not merely:

```text
foo.ts imports bar.ts
```

But:

```text
change: Session ownership semantics

affected concepts:
  Session
  Multiplayer
  Assessment

affected invariants:
  I-17 single authority
  I-31 deterministic replay

affected patterns:
  realtime-state
  session-lifecycle

implementation:
  14 modules

validation:
  8 structural assertions
  17 tests
  3 scenario evals
```

Now planning happens over **meaning**, not filenames.

This is radically different from how coding agents generally work.

# Then comes the really interesting bit

I don't think **generation should be the outer loop**.

Current systems effectively do:

```text
TASK
 ↓
understand
 ↓
plan
 ↓
code
 ↓
test
 ↓
review
```

I'd invert it.

```text
             SYSTEM MODEL
                  │
        ┌─────────┴─────────┐
        │                   │
   desired state       observed state
        │                   │
        └────── Δ ──────────┘
                  │
             transformation
                  │
           implementation
                  │
          reconstruct state
                  │
         measure new Δ
                  │
              reconcile
```

That's a **closed-loop controller**.

The agent isn't being asked:

> "Did you implement the feature?"

It's being asked:

> "Did the repository converge toward the requested semantic state without increasing unrelated divergence?"

That is a much harder target to bullshit.

# And here's another gap I think you're sniffing around

### Agents have essentially no metabolic system for complexity.

Humans notice:

> "This abstraction is getting weird."

> "We've invented three representations for the same thing."

> "This package isn't really a package anymore."

> "That responsibility migrated six months ago."

Agents barely perceive this unless explicitly asked.

So complexity accumulates like metabolic waste.

Your architecture should have a **continuous consolidation process**.

Not occasional refactoring.

Something closer to garbage collection.

Detect:

- duplicate concepts
- competing abstractions
- obsolete compatibility layers
- dead patterns
- responsibility drift
- conceptual aliases
- dependency inversion
- unnecessary indirection
- accidental frameworks
- one-off exceptions becoming conventions

Then propose **semantic compression**.

That phrase may actually matter.

Healthy mature architecture should often become **conceptually smaller**, even while capability increases.

Current agents tend toward monotonic representational growth.

That is practically a slop generator.

# One more level downward

There's a dangerous assumption embedded in nearly every agent framework:

> The repository is the environment.

I think that's false.

The repository is **an artifact generated by the system model**.

Once you accept that, some weirdly powerful things become possible.

A module might be rejected even if:

- it compiles
- tests pass
- lint passes
- feature works

because:

```text
No canonical concept explains why this module exists.
```

🔥

That's the kind of rejection criterion current tooling almost never has.

Another:

```text
This change introduces a second representation
of a concept already represented elsewhere.
```

Another:

```text
This abstraction does not correspond to a stable domain distinction.
```

Those are the failures humans call "this code smells like AI."

They aren't syntax failures.

They're **ontology failures**.

## Which suggests a crisp hierarchy

I might model software integrity as:

\[
\text{Ontology}
\rightarrow
\text{Architecture}
\rightarrow
\text{Patterns}
\rightarrow
\text{Implementation}
\rightarrow
\text{Behavior}
\]

Today's tooling validates mostly upward from the bottom:

```text
Does it run?
Do tests pass?
Does static analysis pass?
```

But slop often originates downward from the top.

Wrong concept.

Wrong ownership.

Wrong boundary.

Wrong abstraction.

Wrong relationship.

Perfectly functioning implementation.

💀

No amount of Jest will save you.

# So I think your instinct is right

There may actually be a missing discipline here.

Not "better AI coding."

Something more like:

> **Computational software integrity engineering**

A framework for preserving and evolving the conceptual identity of a software system under autonomous transformation.

And if you build it properly, Codex/Claude/GPT-whatever are just interchangeable actuators underneath it.

That matters enormously.

Projector then stops being:

> "a clever harness that keeps agents from making a mess"

and becomes:

> **the semantic control plane between intelligence and software.**

That is a much larger and, I think, much more accurate problem statement.

And it gives us a first-principles research target:

### Don't ask "How do we prevent AI slop?"

Ask:

> **What information must remain invariant across an indefinitely long sequence of partially autonomous software transformations for a system to remain coherent?**

Then derive the machinery from that.

That question has teeth. 🧬
