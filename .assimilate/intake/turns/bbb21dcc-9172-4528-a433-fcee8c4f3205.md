# Execution policy

## 1. Do not use microtask decomposition

Override any default methodology that decomposes implementation into tiny 2–5 minute tasks or similarly granular steps.

A task should instead be the **largest coherent independently implementable unit** that:

- has a clear responsibility;
- has a bounded write surface;
- can be validated independently;
- does not require simultaneous mutation of another worker's write surface;
- leaves behind a meaningful architectural capability rather than scaffolding fragments.

Good task boundaries are typically things like:

- one package or subsystem;
- one analyzer family;
- one complete vertical capability;
- one stable interface plus its principal implementation;
- one independently testable execution engine component.

Bad task boundaries are things like:

- create one interface;
- add one schema;
- add one test file;
- implement one trivial method;
- update one barrel export;
- separately review each of the above.

Those should normally happen inside the larger coherent task that needs them.

The purpose is to minimize coordination cost while retaining independent verification.

---

# 2. Build the implementation DAG once

Before substantial implementation:

1. Parse the authoritative specification.
2. Extract architectural invariants and package dependency constraints.
3. Identify implementation units.
4. Determine actual dependencies between those units.
5. Construct a dependency DAG.
6. Identify the critical path.
7. Identify independent work fronts that can execute concurrently.

Do **not** repeatedly regenerate the whole implementation plan after each completed unit.

Update the DAG incrementally only when implementation discovers a real dependency or invalidates a previous assumption.

Persist the DAG and task state in the repository so future contexts can resume it without reconstructing the project plan from scratch.

---

# 3. Optimize for parallel waves

Whenever two implementation units:

- do not depend on one another's unfinished output; and
- do not require conflicting writes to the same semantic ownership region,

they SHOULD execute concurrently.

Use native Codex subagents and isolated worktrees where useful.

Prefer a structure resembling:

```text
                   foundation/contracts/store
                            |
          +-----------------+-----------------+
          |                 |                 |
     analyzers          rule/compiler    transforms/runtime
          |                 |                 |
          +--------+--------+--------+--------+
                   |                 |
              inference         invalidation
                   \                 /
                    +-------+-------+
                            |
                    reconciliation
                            |
          +-----------------+------------------+
          |                 |                  |
        CLI            host adapters     change compiler
          \                 |                  /
           +----------------+-----------------+
                            |
                   end-to-end fixtures
                            |
                    final integration
```

The actual DAG must come from the specification and codebase, not this illustrative graph.

### Parallelism rule

Keep every ready independent work front occupied when practical.

Do not serialize work merely because the specification lists phases sequentially.

Specification phases describe dependency and product maturity, not a requirement that every task in one phase finish before any independent work in another may begin.

---

# 4. Establish shared contracts early

Anything required by multiple parallel workers should be stabilized early:

- public domain contracts;
- persistence ports;
- graph/query interfaces;
- analyzer interfaces;
- model-provider interfaces;
- transform interfaces;
- validation contracts;
- state-digest / transaction contracts.

Workers should program against those stable interfaces rather than waiting for every concrete subsystem to exist.

If an interface must change, evaluate dependent work before modifying it.

Avoid interface churn after parallel implementation begins.

---

# 5. Use worktrees according to write ownership

Use isolated Git worktrees for independent write-heavy tasks when this avoids collision.

Do NOT create worktrees merely as ceremony.

Partition work by semantic ownership.

Examples:

```text
worker A → packages/analyzers/src/typescript/**
worker B → packages/analyzers/src/markdown/**
worker C → packages/core/src/rules/**
worker D → packages/engine/src/authority/**
```

Shared root/configuration files such as:

```text
package.json
pnpm-workspace.yaml
tsconfig*
shared barrel exports
central migrations
CI configuration
```

should preferably be owned by the integration worker or modified through deliberately serialized integration steps.

Parallel workers should avoid casually editing shared infrastructure.

---

# 6. Single integration authority

Parallel workers prepare implementations.

One integration authority owns the canonical branch and is responsible for:

- integrating completed work;
- resolving cross-worker conflicts;
- verifying architectural boundaries;
- running integration validation;
- updating the implementation DAG;
- launching newly unblocked work.

Workers must not independently make incompatible architectural decisions merely to finish locally.

---

# 7. Verification strategy

Verification must be rigorous without becoming the throughput bottleneck.

### During an implementation unit

Run the **narrowest meaningful verification**:

- local unit tests;
- package typecheck;
- package lint where relevant;
- relevant fixtures;
- interface contract tests.

### At integration/wave boundaries

Run broader checks:

- dependent package tests;
- repository typecheck;
- integration fixtures;
- architecture constraints;
- reconciliation tests.

### At major milestones and before completion

Run the complete required quality gates from the specification.

Do not run the entire repository test suite after every trivial edit when dependency-local tests can prove the intermediate step.

---

# 8. Review policy

Use targeted independent review, but avoid redundant ceremony.

For a normal coherent implementation unit:

1. implement;
2. verify locally;
3. perform a focused spec-compliance review;
4. perform code-quality review only where it adds information;
5. fix concrete findings;
6. integrate.

Do not repeatedly reread or re-review unchanged portions of a large implementation.

Review should be **delta-scoped**.

At integration boundaries, perform broader architectural review over the combined change.

For high-risk kernel components such as:

- canonical state;
- semantic hashing;
- authority;
- rule composition;
- invalidation;
- transaction recovery;
- reconciliation;

use stronger independent/adversarial review.

Routine adapters and glue do not need the same review intensity.

---

# 9. Context policy

Do not make every worker reread the entire authoritative specification.

The orchestrator should compile bounded task context containing:

- task objective;
- applicable specification sections;
- relevant architectural decisions/invariants;
- stable public interfaces;
- dependencies;
- write scope;
- forbidden scope;
- relevant fixtures;
- completion criteria.

Workers may retrieve additional specification context when necessary.

Maintain durable implementation notes for facts that future tasks will otherwise have to rediscover.

Avoid repeatedly spending model context rediscovering settled architecture.

# 10. TDD without ceremony explosion

- graph semantics;
- rule composition;
- hashing;
- invalidation;
- authority;
- transactions;

- selectors;

**Do not turn every tiny implementation step into its own test-plan / red / green / review / commit ceremony.**

Treat the coherent implementation unit as the TDD scope.

A worker may create several related failing tests and then implement the subsystem necessary to satisfy them.

The goal is executable correctness, not process theater.

---

# 11. Commit strategy

Prefer one focused commit per coherent completed implementation unit or integration boundary.

Do not produce dozens of commits for trivial internal steps unless rollback value genuinely warrants them.

Every commit must:

- represent a meaningful state;
- pass the verification appropriate for its scope;
- avoid unrelated changes.

---

# 12. Critical-path scheduling

Continuously identify the implementation critical path.

Prioritize work that:

- unblocks many downstream units;
- stabilizes shared contracts;
- exposes architectural mistakes early;
- enables end-to-end testing;
- reduces uncertainty for other workers.

Do not spend all available workers on peripheral adapters while a core dependency bottleneck is blocking half the graph.

When useful, allocate:

- one worker to the critical path;
- remaining workers to independent non-critical ready tasks.

---

# 13. Vertical slices before broad abstraction

Follow the specification's mandated vertical-slice philosophy.

Get the core Projector loop working end-to-end early:

```text

→ establish/consume authority
→ compile rules
→ detect divergence
→ plan deterministic repair
→ mutate
→ validate
→ reconcile
→ produce cleanup/certificate state
```

Use the misplaced repository-script fixture or equivalent specification-mandated wedge.

Do not build every generalized adapter, external surface, UI, or future abstraction before proving this loop.

After the first vertical slice works, broaden the implementation in parallel.

# 14. Deterministic implementation over agent improvisation

When the specification defines deterministic behavior, implement deterministic machinery.

Agents are implementation workers, not runtime substitutes.

Do not satisfy requirements such as:

- selector composition;
- invalidation propagation;
- canonical hashing;
- transaction recovery;
- rule conflicts;

- state digests;

# 15. Avoid speculative abstraction

Do not create:

- a package per noun;
- unused extension frameworks;
- generic providers with only hypothetical consumers;
- abstractions unsupported by the current specification;
- adapters before their contract is exercised.

Honor the interfaces required for future growth, but implement only the abstraction necessary for current or explicitly planned consumers.

If a subsystem can remain internal until a second implementation proves a boundary, keep it internal.

---

# 16. No phase ceremony

Do not stop after every specification phase merely to produce a report and wait for permission.

Proceed automatically through ready DAG nodes unless:

- the specification requires explicit human approval;
- an actual architectural contradiction exists;
- necessary information is unavailable;
- an operation would cross a configured safety boundary.

Phase completion may be recorded, but should not introduce unnecessary idle time.

# 17. Failure handling

When a worker fails:

1. preserve its useful findings;
2. classify the failure;
3. determine whether the task definition, architecture, or implementation is responsible;
4. resume or repair the same unit when appropriate;
5. do not restart the entire planning process.

When integration exposes a conflict:

- resolve the narrow conflict;
- update affected DAG edges;
- revalidate downstream assumptions;
- continue.

Do not globally invalidate unrelated completed work.
