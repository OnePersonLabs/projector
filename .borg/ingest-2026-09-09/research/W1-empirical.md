# W1 -- empirical maintainability evidence

Research completed 2026-09-10 against recipient `043a7c32e62f3e8319fe5a0e4bfc54d949a9f096`. Investigation and design only. No donor benchmark or paid model run was executed. Repository source and primary publication checks establish what exists and what was reported; they do not reproduce the experimental results.

The useful transfer is a controlled, longitudinal evaluation of retained behavior and total maintenance cost. Neither paper establishes that lowering a static score improves downstream correctness, nor that Projector produces an economic advantage. Existing Projector meaning already requires fresh-session comparison and state-bound runtime evidence. These donors sharpen the experiment and its failure analysis; they do not justify another requirements store or an automatic quality authority.

## CodeThread: what survives verification

CT constructs two steps by removing function bodies from a benchmark base, generating restoration instructions, and admitting an agent restoration only when all prior passing tests still pass and all target failing tests still fail. It then gives the original downstream issue to an agent on either original human code (HA) or restored agent code (AA). The human base is historical source, not a newly recruited human following the same generated restoration prompt. Existing signatures and surrounding architecture are supplied. This measures downstream agent success under this controlled reconstruction, not general human maintainability or unconstrained architecture design (CT 66--84, 226--248).

The matched-code comparison is valuable: it holds the downstream task fixed instead of confusing harder future requests with worse inherited code. However, admission is model dependent, removes incidental early solutions, and introduces selection bias. Claude and GPT runs on three datasets are further restricted to cases passing two other models' initial gates. One run per model/condition/instance does not estimate run-to-run instability. Cost limits can affect models differently. No AH human-maintainer arm exists (CT 96, 100, 168--170, 242--248).

## SlopCodeBench: what survives verification

SC deliberately carries each agent's actual workspace through 3--8 evolving checkpoints while resetting the container, packages/session state and conversational context. Hidden tests use CLI/API boundaries; specifications prescribe external behavior instead of internal implementation. The evaluated track is Python, despite language-agnostic task contracts. Problems were selected partly by excluding ones frontier agents solved in one shot. This is a useful stress test, not a representative sample of software work (SC 44--78, 114--159, 800--839).

Its scoring decomposition is essential. Strict requires every applicable test, isolated excludes prior-checkpoint regression tests, and core measures the explicitly described subset. Missing future checkpoints count as failures for correctness but are excluded from code-quality statistics. Therefore strict, category-specific behavior, survival/attrition and metrics must be reported together (SC 116--137).

| Claim | Verified interpretation and limitation |
| --- | --- |
| Best passes 14.8%; none solves a problem | Paper v2 covers 36 problems, 196 checkpoints and 15 models, often with different native harness versions. GPT 5.5 reaches 14.8% **strict** and 28.1% **isolated** checkpoint solve rates. No evaluated run passes every checkpoint of a problem; this does not mean every final artifact fails or that only 14.8% of tests pass. SC 159--181. |
| 77% erosion, 75.5% verbosity growth | Fractions of produced-code trajectories with increasing measured proxies, not defect incidence, causal technical-debt estimates, or a probability any agent edit is harmful. Fresh requirements and program size grow concurrently. SC 145, 193--197. |
| Agent code is 2.3x verbose and 2.0x eroded; grows 6.6x/5x faster | Calibration against 473 heterogeneous Python repository histories and 13,667 sampled commits, not matched humans performing identical tasks. Commits and checkpoint requests have incomparable granularity, maturity, review and selection. Temporal pre/post-2024 changes cannot identify AI assistance causally. SC 199--209, 1074--1092. |
| Quality prompts cannot stop degradation | Three GPT models have prompting variants and a MiniMax anti-slop run; this is not every possible prompt or workflow. `plan_first` also adds refactoring/style rules, and anti-slop adds example testing and focus instructions, so these are bundled treatments. GPT 5.4 anti-slop improves start-to-end quality in the authors' own account. No result tests Projector's typed meaning and reconciliation. SC 211--221, 873--1072. |

**Proxy definitions and gaming.** Erosion weights each callable by CC times square root of source LOC, then divides high-CC mass (strictly CC > 10) by all callable mass. Splitting decisions into sub-threshold helpers can reduce the score while worsening cohesion; adding low-complexity code can dilute it; moving work to a library can move complexity outside measured scope. Verbosity combines rule-hit and clone coverage: policy-driven/generated duplication, readable single-use variables, and necessary validation can be legitimate. Removing an error guard can improve a style score while violating the input contract. Do not turn these scores into promotion gates or an optimizer reward without behavioral constraints. The current source confirms the CC > 10 calculation. [Pinned mass calculation](https://github.com/SprocketLab/slop-code-bench/blob/06b5c0687d4c05ee502e9696a4d0c22fc1eec5e0/src/slop_code/metrics/checkpoint/mass.py)

SC Appendix B.3 itself reports almost no association between erosion and next-checkpoint passing (-0.018), and only .167 with cost; raw LOC predicts cost more strongly (.502). Sensitivity to several cutoffs does not establish construct validity or causal benefit. This agrees with CT's warning that static maintainability proxies miss behavioral changes, rather than contradicting it (SC 792--798; [primary Table 6](https://arxiv.org/html/2603.24755v2#A2.T6)).

**Contradictions requiring restraint.** These originate in the supplied paper or missing transcription, not independently established experimental failures:

- SC 181 names Opus 4.5 as the 67.3% core winner; Tables 1/8 assign that number to Opus 4.6. Its abstract says improvement up to a third, whereas RQ4 says up to 62.3% initial erosion reduction; initial, overall and model-specific effects must remain distinct.
- SC 37 says a 2.3-point correctness decrease; SC 221 reports 2.4 for anti-slop and 3.6 for plan-first. Different included models can explain some aggregate differences, but the scope must be explicit. These do not support a universal planning penalty.
- SC 1092 calls FastAPI verbosity .273 above agent mean .44; the numbers contradict the sentence. SC 690 calls a filtered list comprehension an identity comprehension, and removing its early empty-rule check would introduce file reads the shown code currently avoids. The excerpt does not prove those choices are waste.
- The complete code-search example orders matches lexicographically by file at SC 422--424, but checkpoint 2's example emits `src/engine.cpp` before `main.py` at 486--490. Without explicit supersession this contradicts the prior rule. Hidden-test strict failure may expose a specification defect, not an agent design failure. Adjudicate the contract before scoring.
- Current [website leaderboard](https://www.scbench.ai/) lists 19 models and different verbosity values (e.g. GPT 5.5 .269 versus paper .32); its present metrics documentation delegates composite scores to pinned `scb-check`. Pin publication, source, metric version and population together. Do not merge live leaderboard scores with paper ratios. | Candidate | Value and required dependencies | Distinctiveness and falsifier |

## Concrete experiment design for the existing goal

Design, not authorization to launch paid runs:

1. Select three independent, representative Projector change chains before observing outcomes. Each contains an initial change plus at least two dependent follow-ons, including a behavior-preserving refactor and an intentional contract change. Use the same initial repository revision and user requests in paired arms: Projector context/reconciliation versus a capable agent with ordinary search, source, tests and concise durable notes. Hold model, harness version, resource ceilings and tool permissions equal. Randomize arm execution order and keep workspaces isolated.
2. Start every follow-on in a fresh agent session on its own arm's actual prior artifact. Preserve each arm's permitted notes/accepted meaning; do not replace failed code with a gold solution. Run a separate matched inherited-artifact swap only if needed to distinguish tool benefit from code-quality benefit. Mark any intentionally synthetic perturbation separately.
3. Prepare an evaluator from accepted external behavior before implementation. Include ordinary inputs, malformed/absent values, documented exception/error responses, side effects, retained scenarios and the intended new behavior. Keep holdout inputs hidden from implementing agents; provide enough specification to derive their expectations. Visible repository tests remain available in both arms, reflecting the capable baseline. Resolve contradictory specifications before scoring, not by inventing expected behavior after a failure.
4. Include a targeted fresh-session stale-knowledge probe and an unrelated-edit negative control. The affected claim must become stale or suspect without automatic loss of unrelated valid reasoning. In a disposable evaluation copy, seed an input-default or exception-handling drift that passes an existing happy-path test. Show that a new targeted observation detects it; restore just that change and rerun the same failing case before attributing cause.
5. Record every checkpoint's strict/current/error/regression results, host completion/failure, changed surface, human repair/review time, setup/retrieval/reconciliation/test time, input/output/cache tokens and actual monetary accounting. Charge initial knowledge creation and subsequent repair to the Projector arm. Keep raw units and prices separate; a shorter context is not itself lower total cost. Report unsuccessful/aborted chains as such, with measured partial expenditure and collection unknowns.
6. Treat three chains as a feasibility pilot, not a population estimate. Publish individual paired outcomes, failures and sensitivity to setup amortization. Predetermine the next experiment size from observed variance and the minimum economically meaningful improvement; do not choose it to obtain significance. Only a sufficiently replicated comparison preserving required correctness can support a bounded advantage claim. Otherwise report no demonstrated advantage and retain the functional evidence for what it actually covers.

Example user story: a fresh agent must extend an existing selector/CLI error contract without reviving a previously rejected fallback. It should retrieve why the fallback was rejected, preserve existing malformed-input behavior, implement the accepted extension, and invalidate only claims whose dependencies changed. Evidence must show the actual CLI observations and subsequent maintenance work in both arms, including time spent finding and repairing stale knowledge. A stored decision, lower verbosity, or a matching hash does not by itself satisfy this story.

## Rejected or deferred conclusions

Reject universal claims that agent code is inherently unmaintainable, that static scores measure debt causally, that planning is ineffective, or that these publications demonstrate Projector's value. Reject blanket bans on guards, helpers, duplication or single-use names. Reject corpus-wide new quality gates, donor prompt injection into every host instruction, and a donor-shaped benchmark subsystem.

Defer exact donor effect-size reliance pending raw-cohort reconciliation, repeated-trial uncertainty and metric-version reconstruction. Defer general browser/service evidence machinery: the accepted runtime-evidence requirement already demands a concrete application adapter first. Defer human-maintainer conclusions pending an actual human comparison. The present endpoint is a native, falsifiable experiment and evidence design; implementation, exercise and measured advantage remain separate future states.
