## Decision-ready findings

1. **Repository change capture, exact approval, application, and crash recovery are public.** Their production executor supports exactly one accepted mutation packet. This is the foundation to extend.
2. **General packet orchestration is an internal kernel, not the production write executor.** Current `WorkPacket` and `ExecutionPlan` contracts lack typed candidate results and joins. Wiring a second executor into the CLI would create incompatible recovery/completion authorities.
3. **Application evidence is still missing integration.** Existing validators provide useful isolated Node execution with tracked source identity, but are read-only and network-denied. Operational telemetry describes Projector, not the application under test. A browser or telemetry schema cannot close this gap.
4. **The generic host-run path is too weak to authorize collaboration completion.** It reuses saved state digests, overclaims host feature probes, and checks limited parser failures. Candidate host reports must remain untrusted input to fresh repository validation.
5. **Start bounded collaboration with imported host candidates.** Authenticate their immutable bytes, state dependencies, and typed join at final proposal capture. Keep the one accepted mutation packet, writer lease, transaction journal, and recovery path. Native orchestration before the first proposal is a separate later increment.
6. **Economic advantage remains unestablished.** Benchmarks contain real accounting and invariant controls, but those are not a held-out repeated-change comparison against a strong ordinary agent.

## Hidden dependencies and circular proof risks

- **Hashing versus authority.** Caller-created content hashes show byte consistency. They do not authenticate an external actor, a browser run or a claim of independence. New adapters need a trusted producer boundary and checked currentness, not simply a `ValidationResult` with `strong` assurance or an `independent-agent` lane.
- **Validator dependency cone.** Current independent source capture pins the entry file and allows reads across the repository. An imported helper, runtime library, application configuration, seed data or environment can affect results. Bind those actual inputs or conservatively invalidate the bounded manifest; never infer entry-file identity proves the entire observation dependency cone.
- **Coverage can be operational but violated.** An executed lens contributes enforceability whether its result is satisfied or violated. A code-to-requirement membership contributes mapping even when behavior has no test. Application measurements must identify their scenario, predicate and bound state separately.
- **Two execution authorities.** `executePacketPlan` and the public `StateBoundChangeExecutor` have different port/result/artifact models. A generic coordinator cannot be made public by calling it alongside lifecycle recovery and then treating either receipt as sufficient. The first collaboration increment should avoid concurrent accepted mutations and a second transaction route entirely.
- **Unknown future edits cannot be approved concretely.** Candidate exploration happens before exact edit/proposal hashes exist. `compiler.ts:900` makes intent identity depend on proposal hash; `engine/change/compiler.ts:140-141` makes SemanticChange identity depend on semantic fields and state binding. `store.ts:216-250` saves immutable captures keyed by that identity. Mutating a capture in place to incorporate later candidates would invalidate its reviewed authority.
- **Same-state-looking host changes.** Two versions of a dirty file can share Git porcelain status; HEAD can remain unchanged. The current host adapter's copied/synthetic digests therefore cannot admit candidate results. Use `observeChangeRepository` and the existing dependency-scoped validator before joins and accepted writes.
- **Snapshot versus recreation.** A fresh clone can recover committed meaning and adapter configuration; it cannot truthfully reconstitute an uncopied browser session, external service state or captured diagnostics. Missing runtime artifacts must remain unavailable and require a new run.

## P1 -- concrete application evidence, native seams

Start from one Psychord browser/input/audio scenario and its actual setup, readiness, exercise and teardown. Make the provider's isolation and local endpoint policy explicit. Existing validators deny all network and all repository writes; provisioning and browser-to-application communication require a separately capability-proven application-run boundary. Do not silently broaden `KnowledgeValidatorRun` or use its source-level independence as application-run authority.

Candidate implementation areas:

- `core/domain/contracts.ts` and corresponding schemas: a minimal typed application observation envelope that references accepted scenario/predicate identities, `StateBinding`, provider/version, run and environment/configuration/fixture identities, artifact content hashes, measurements/units, observed outcome and incompleteness. `ValidationResult` remains the common conclusion; its freeform `details` cannot be the only lifecycle contract for externally produced evidence.
- `runtime/execution/` and existing worktree/path/lease components: provision and clean up the concrete isolated run with bounded resources, process lifecycle, endpoint scope and interruption recovery. Own raw immutable observation artifacts as derived execution evidence, not canonical truth.
- `integrations/`: the actual browser/diagnostic provider; retain useful logs/traces/screenshots with inspected producer identity and sensitivity controls. Expose only the real provider capabilities. Avoid depending on CLI internals from runtime or engine.
- `control-plane/change-lifecycle/executor.ts`, `knowledge/validators.ts` and `knowledge/governance.ts`: admit provider observations through a common authenticity/currentness check, then map their concrete assertions into required validation. Reconciliation invalidates changed scenario, provider or relevant run inputs. Unsupported providers produce unknown/unavailable.
- `control-plane/coverage/service.ts`, `knowledge-cli.ts`, and later `mcp-cli.ts`: disclose exercised scenario evidence and limits through existing reads. Add callable MCP tools only with production handlers and real survival coverage.

Completion must be checked against the observed application at the bound state. Successful setup, a zero exit code, a generated screenshot, or a copied historical result is insufficient. Same-packet tests may support validation but must retain their provenance and cannot masquerade as independent acceptance.

## P2 -- minimal bounded collaboration without a second workflow store

**Recommended first increment:** parallel host-owned read/candidate production, one typed join, then one serial accepted repository mutation through the current lifecycle. This supports bounded collaboration without promising a general DAG scheduler, parallel writers or native pre-proposal agent resumption.

Before capture, the host retains candidate artifacts. Candidate work identity derives from the work contract and saved context, not from a future SemanticChange ID or result bytes. During `capture`, Projector imports exact candidate bytes, validates declared result shape, verifies producer/provenance constraints and dependency currentness, and computes a join result. The joined concrete `ChangeProposal` still passes the existing identity, architectural-product, authority, scope and validator checks. Proposal capture establishes the immutable relationship among candidates, join and accepted-write plan; approval remains over that concrete plan after final candidate production.

Existing contracts already carry useful primitives: `ExecutionPlan.packetIds/checkpoints/completionCriteria`, `WorkPacket.dependencies/boundState/capsuleId`, and `ExecutionCapsule`'s allowed writes, requirements, scenarios and validations. They **do not** define candidate output schema/version, required producer roles, attempt identity, predecessor-result hashes, join decision or effect distinction. `LifecycleCaptureRecord` stores plans/capsules, not full work packets. `ChangePacketProposal` currently requires nonempty write selectors and rejects all overlapping units/semantic owners (`engine/planning/change-plan.ts:26,35-39`), so read-only candidate work should not be forced through that mutation-packet compiler.

Minimal extensions:

1. Add typed candidate-result and join-proof input contracts beside existing change-proposal/capture contracts. Each result binds its work-contract hash, source context/dependency proof, producer attempt, artifact hash and declared result kind. Joins require the specified inputs, detect conflicts and return an accepted/rejected/needs-work outcome with reasons; a result hash or role label never grants canonical authority.
2. Extend `CaptureRepositoryChangeInput`, compiler capture input and `LifecycleCaptureInput/Record` with authenticated candidate/join attachments. Copy immutable artifact bytes into the existing lifecycle artifact ownership; include their hashes in the proposal/plan's derived dependency proof so approval cannot be reused after substitution. Keep all storage under the current lifecycle owner and reuse path checks/content addressing.
3. Derive resumable inspection and review from imported captures plus immutable result attachments. Repeating identical capture/import is idempotent. Changed candidate bytes or changed exact edits require a new capture/approval; an explicit predecessor-capture reference may preserve inspection continuity. Do not retrofit an unapproved mutable revision into current immutable capture semantics.
4. Leave accepted application in `RepositoryChangeLifecycleService` -> `executeCompiledRepositoryChange` -> `StateBoundChangeExecutor`. Reuse `WriterLeaseManager`, `FileTransactionJournal`, prepared-success publication and `recover/resume`. No generic packet executor, new task journal or accepted-status ledger is required for this increment.

If a later real workload requires native candidate execution before the first proposal, specify that as a separate capability with bounded read authority and new public survival evidence. It is not already supplied by `WorkPacket.status`, a host subagent flag, or the internal packet coordinator. If later accepted writes must be split, extend the existing lifecycle's packet attempt and receipt ownership rather than adopting an incompatible executor.
