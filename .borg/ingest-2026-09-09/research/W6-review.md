## Findings

### F1 -- high: contribution attachments do not yet participate in the identity that must change

**Affected:** [DESIGN D3](../DESIGN.md), particularly original line 86; [P2 design and P2.3--P2.4](../proposals/P2-contributions-and-continuation.md).

The design imports contribution bytes as immutable attachments under the resulting lifecycle identity and promises that changing any contribution requires a new capture/approval. It does not specify a contribution/join digest in the strict proposal, bound state or immutable plan. Equal edits and equal repository state with changed review evidence can therefore retain the same SemanticChange ID and plan hash. Adding attachments only to the capture record produces an immutable-capture collision; leaving attachments out of approved identity permits reuse of authority across changed required evidence.

**Verified source:** `packages/control-plane/src/change-lifecycle/compiler.ts:900` derives intent identity from `proposalHash`; `packages/engine/src/change/compiler.ts:140` hashes semantic fields and bound state; `packages/control-plane/src/change-lifecycle/store.ts:216` captures under SemanticChange identity, with conflicting immutable data rejected at `:244`; approval authenticates the plan/capsules at `:260` onward. W4's minimal extension explicitly calls for candidate/join hashes in the proposal/plan proof, which synthesis omitted.

**Required repair:** define the exact digest-bearing input: canonical ordered contribution-set content, the join contract/version and resolved result, with required/optional omissions. Bind it through a versioned strict proposal and immutable plan/capsules before computing capture and approval identities. Freeze bytes before compilation and authenticate them at relevant lifecycle use points. Preserve legacy hash/read domains and historical recovery receipts. Add the planned survival case **same edit bytes and repository state, different required contribution evidence**: new identity and approval are required. Identical frozen input must remain idempotent.

### F2 -- high: P1 postpones its central architecture choice while presenting an implementable adapter design

**Affected:** [DESIGN D1--D2](../DESIGN.md), [P1 design/P1.1/P1.3/P1.4](../proposals/P1-application-evidence.md), [EVIDENCE unresolved frontier](../EVIDENCE.md).

P1's first task still selects a real scenario and oracle; later tasks say to add a proven private application profile and implement the first adapter. No selected application entrypoint, platform mechanism, build preparation path or trusted collection root is specified. “Authenticated manifest” describes the desired conclusion but not who creates it outside candidate application control. A private environment protecting the host does not itself prevent the application under test from substituting evidence or influencing a controller that shares writable state. The actual scenario can materially change the runtime choice, browser fidelity, device access, resource policy and achievable oracle. Calling all these implementation questions disguises the remaining design decision.

**Verified source:** the current `scenario:inspect-isolated-application-behavior` is a generic Projector integration commitment, not an actual Psychord behavior oracle. `packages/runtime/src/execution/wsl-sandbox-launcher.ts:78` accepts only the configured Node executable; its per-launch mounts/process invocation do not supply a composed application/browser environment. `sandbox-launcher.ts:21` probes read/write visibility and denied network, not the proposed application/controller trust lane. The accepted runtime requirement expressly leaves generic browser authentication/provisioning unrealized.

**Required repair:** select one real existing Psychord scenario now from read-only source evidence and name its expected/forbidden behavior. Choose the smallest concrete platform/run profile, staged build/fixture inputs, app/browser communication mechanism and trusted collector custody. State how candidate app code is denied write access to controller/manifest authority, how launched bytes and endpoint are observed, and what platform/observable limits remain. Turn P1.1 into implementation of that selected design and capability probes. A demonstrated successful run can remain a later implementation requirement; an unchosen proof mechanism cannot.

### F3 -- medium: P3's mandatory task sequence still assumes every repair produces a reusable rule

**Affected:** [P3 P3.1/P3.5/P3.6](../proposals/P3-correction-and-governance.md).

P3 correctly allows a one-off local repair and says generalization requires additional evidence. Its task table nevertheless requires a shadow lens evaluation for “the selected proposed reusable correction” and routes the accepted correction through architecture products. A concrete first failure may have no recurring producer or faulty accepted rule; requiring those tasks then manufactures the policy work the proposal explicitly rejects.

**Required repair:** make shadow evaluation and architecture-product mutation conditional on an actually selected reusable enforcement or architecture revision. A local code/test/adapter correction should complete through the normal exact change lifecycle, with the exercised failure and preservation of unrelated work. Keep one deliberate harmful-rule case as validation of the promotion boundary if desired; do not require an enforced rule as the output of the first real repair.
