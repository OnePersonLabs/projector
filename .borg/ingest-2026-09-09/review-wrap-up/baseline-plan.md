## Decision: prevent divergence without building a second system

Typed canonical records own accepted conceptual meaning throughout the transition, not only after deletion. PROJECTOR_SPEC is fallible source evidence and a synchronized transitional representation; conflicts are resolved through reviewed canonical acceptance/revision, never by whichever file was edited last.

Keep PROJECTOR_SPEC only for the finite transition. Task 1 first audits drift and applies one coherent, evidence-reviewed correction to affected source sections and canonical meaning. Afterwards correct affected sections alongside each accepted semantic/interface change; do not rewrite all 43 modules for style and do not build a temporary Markdown framework. Corresponding canonical meaning, source sections and stated implementation status must agree within each completed change batch. Keeping intended behavior separate from actual delivery is required; synchronizing the spec does not mean weakening it to match unfinished code.

Prepare the full source-to-canonical accounting early, update it as affected material changes, and rehearse import/cutover in a disposable clone. Freeze the exact final source revision only during the final cutover. In that same coherent change, accept the remaining useful meaning, switch the last consumers, and delete PROJECTOR_SPEC. There is no post-cutover manual spec to maintain.

After retirement, canonical conceptual records own accepted meaning; executable typed contracts own exact machine shapes; public human/agent views derive from those owners. Historical Git locators may remain as provenance, but fresh operation cannot need historical Markdown. Do not copy the old tree elsewhere or import one giant blob and call that ingestion.
