# Interpret the source pile

This page governs how assimilation translates heterogeneous chats and documents into its working synthesis. It applies to this fileset as well as future intake. Source material is evidence about intent, proposals, events, or technology; its wording is not automatically the structure or authority of the output.

## Name the two systems differently

An **assimilation topic note** is one Markdown file that develops a coherent subject within the working synthesis. It may cover a principle, mechanism, tradeoff, research question, or candidate change. A topic note has a local filename and ordinary Markdown links. Its structure can evolve as understanding improves.

A **Projector concept record** is a typed accepted entity within Projector's canonical model. Projector also has other accepted entities, including requirements, scenarios, decisions, and relationships. A topic note can discuss any of them without becoming one. File names and titles in assimilation do not imply Projector IDs, equivalence, adoption, or synchronization.

Use **working synthesis** for the whole assimilation fileset. Use **change intent brief** for a bounded result prepared for Projector's existing change workflow. Do not use “conceptbase,” “concept file,” or “canonical concept” as names for assimilation storage. The word *concept* remains appropriate when discussing actual concepts in cognition, the research proposals, or Projector's typed concept records; clarify which sense is meant when a decision depends on it.

## Translate what a source meant

Older chats used “concept” broadly. Resolve each instance by its function:

| Source usage | Assimilation reading |
| --- | --- |
| “One concept per Markdown file” in a handoff or context design | A proposal for cohesive **topic notes** and progressive disclosure. It does not dictate Projector's record boundaries. |
| “Projector concept” with an actual accepted identity | A claim about a **Projector concept record**; inspect current Projector state before relying on it. |
| “Concept as dynamic relational organization” | The research **subject** of the semantic-dynamics topic, with the word concept retaining its theoretical meaning. |
| `§name` or a bracketed rendered view | A proposed project-concept reference convention. It is not an implemented syntax for assimilation topics. |
| “Semantic context compiler” | A proposed Projector capability to evaluate separately; assimilation may prepare its own worker context without inheriting that architecture. |
| “The assistant initially proposed X; the user corrected Y” | State the resulting meaning and the consequential reason. Preserve history only when necessary to understand a live alternative or evidence gap. |

A source claim may be an accepted user constraint, a suggestion, an observation about an earlier repository revision, a quotation inside a chat, or an assistant's extrapolation. Do not promote them to the same status because they appear in one handoff. Repeated text from branched ancestry counts once as evidence; a sibling branch does not automatically overrule another. Resolve genuine current differences from scope and later clarifications. Keep a material unresolved difference visible and ask the user when it changes the next consequential decision.

Treat the current user clarification as governing here: cost-conscious route selection and refusal of automatic quality downgrades under low quota are compatible. The route includes model, effort, task boundary, delegation, context, verification, and expected repair burden. Do not turn historical model suggestions into current measured rankings.

## Produce a usable final state

Write topic notes as current understanding, with operative detail and limitations. Do not put source IDs or per-paragraph citations into ordinary topic notes merely because a quoted handoff demanded them. Do not make ordinary reading depend on original source chats, attachments, transcript timestamps, or URLs standing alone. Keep selective recoverable evidence behind the view when later audit or reinterpretation matters, and state when a source was capped or unavailable. “Lossless conceptual squash” is a fidelity target, not a guarantee.

The change intent brief extracts a decision-ready candidate from one or more topic notes. It carries the substance Projector needs to investigate, but does not preassign a Projector ID merely because a topic note has a convenient slug. Projector resolves current identity and authority in its own workflow. Assimilation records the outcome as new input when useful; the result does not retroactively turn its topic note into a Projector record.
