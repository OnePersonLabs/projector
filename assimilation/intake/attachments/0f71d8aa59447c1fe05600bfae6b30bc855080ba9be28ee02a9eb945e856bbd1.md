# Projector: Quality-Frontier Execution

## Joint allocation of cognition, context, verification, and parallel work

**Date:** September 11, 2026  
**Status:** Design proposal for synthesis and staged implementation, not an amendment automatically applied to Projector's accepted specification.  
**Immediate recommendation:** Keep the current Projector implementation owner on **GPT-6 Astra / High**. Introduce cheaper specialists only for bounded work whose complete execution-and-verification path earns the saving.  
**Core policy:** Optimize durable quality and lifecycle efficiency. Do not degrade competence because an allowance is running out.

> Spend intelligence where it changes the result. Reduce the amount of work that requires intelligence before reducing the intelligence assigned to it.

## 1. Executive decision

Add a **quality-constrained execution-policy compiler** inside Projector's existing planning and Execution Capsule machinery. Do not build a separate orchestra of agents to decide how many agents to launch.

For each coherent work unit, choose the following together:

```text
semantic boundary
+ responsible owner
+ model and supported reasoning effort
+ context to retain, retrieve, or delegate
+ sequential / read-only delegate / isolated writer topology
+ verification and integration obligations
+ stop and escalation rules
```

These choices are coupled. A model that is economical inside a stable contract may be uneconomical when it must discover that contract. Parallel writers that are individually fast may be collectively slow when they share unsettled assumptions. A cheap patch can become expensive when the integrator must reconstruct its reasoning.

The starting configuration is deliberately asymmetric:

| Responsibility | Initial routing proposal |
|---|---|
| Ongoing architectural understanding, implementation judgment, integration | Astra / High, retaining coherent context |
| A bounded unresolved problem with material consequences | Astra / XHigh when additional reasoning has a concrete job |
| Complete implementation behind stable contracts | Sol / High when task-family evidence supports equivalent quality |
| Repeatable, narrowly verifiable leaf work | Luna at a supported, evaluated effort; initially read-only or quarantined outputs |
| Very low-latency, bounded coding work | Optional Codex-Spark lane, capability- and quality-gated |
| Exactly specified transformations, querying, test execution, accounting | Deterministic tools rather than an LLM |

This table is a cold-start policy, not a measured performance ranking. Sol / XHigh, Terra, and other supported configurations remain candidates when evidence establishes a useful niche. Do not force every model into the production workflow simply because it exists.

The most important departure from the earlier proposal is:

> A strong owner should retain ambiguous, tightly coupled work. It should delegate out of competence, not delegate first and purchase competence only after failure.

## 2. Source boundaries and integration intent

This document distinguishes three bases:

**User requirements.** Preserve quality, completeness, architectural coherence, and sound judgment; optimize total cost including future correction; avoid manual model shifting; make scarcity controls optional; use parallelism only when it pays.

**Attached Projector material.** The supplied SDD/semantic-holon review describes Change Cases, scoped Relevance and Impact Closures, state-bound Execution Capsules, independent evidence, single integration authority, and reusable learning. The supplied throughput handoff favors coherent units, bounded worker context, incremental DAG maintenance, and worktrees according to ownership. The architecture-decision review favors materiality-triggered decisions with scoped validity. The Persistent System Conception attachment is a summary of a larger proposal, not the full proposal. Its learning ambitions inform compatibility, not a claim that a learned scheduler already exists. [P1-P4]

**Current platform research.** Section 16 records official Codex capabilities checked on the date above. Availability in a particular installed client or account still needs a runtime probe. [W1-W9]

No live Projector repository or current local wrap-up plan was inspected for this proposal. References to Projector components describe the supplied design material, not verified implementation status. In particular, the dated repository-progress claims inside the attached review are not treated as current status.

### Preserve versus revise

Retain coherent ownership, bounded context, explicit proof obligations, delta-scoped review, and one integration authority. Revise the throughput handoff's instruction to keep every independent work front occupied: independence is necessary for safe parallelism, but is not sufficient to make parallelism worthwhile. [P2]

Retain the materiality threshold from progressive architecture decisions. A routing decision needs durable identity only when it affects reuse, explanation, execution, or learning. Most routine invocations should reference a policy version rather than create another elaborate decision document. [P3]

Semantic holons, where adopted, can contribute affected invariants and ownership concerns. They do not each receive a standing model agent, vote on model choice, or run their own independent scheduler. The durable entity is not an LLM session. [P1]

## 3. Define the sweet spot correctly

The desired operating point is the **highest useful competence whose marginal benefit still justifies its total incremental cost**. It is not the cheapest model that can sometimes pass tests, nor maximum effort everywhere.

Three safeguards prevent this becoming an empty slogan.

### 3.1 Quality is a vector, not a passing test count

Assess at least:

- behavioral correctness and requirement completeness;
- architectural coherence, ownership, and contract preservation;
- maintainability, unnecessary complexity, and duplication;
- relevant failure handling, observability, and recovery;
- quality of independent evidence;
- unresolved assumptions and likely downstream repair.

Material deficits on one dimension cannot be averaged away by attractive prose or success on easy tests. The accepted task defines mandatory quality obligations. The router cannot weaken those obligations to make a cheaper route qualify.

A validated patch is not proof of the absence of every defect. Validation supplies bounded evidence; uncertainty remains explicit.

### 3.2 Evaluate whole execution plans

For a candidate plan `a`, estimate lifecycle cost over the same work scope and observation horizon:

```text
C(a) = owner work
     + worker work
     + context construction and duplication
     + routing and consultation
     + review and deterministic verification
     + worktree setup and integration
     + observed rework
     + estimated unresolved downstream liability
```

Measure wall-clock completion separately, including queueing and the integration critical path. Human corrections are a separate burden, not free labor.

Keep main-pool usage, any genuine separate-pool usage, API spend, compute time, and human effort as a resource vector. A separate allowance can make one route attractive without making its engineering cost zero. Do not pretend API dollars and subscription allowance percentages are interchangeable.

A cost is counted once. For example, observed repair is actual cost, while future repair estimates apply only to unresolved exposure. They are not added twice under different names.

Use explicit parent/child event lineage and identify whether a reported total already includes descendants. Do not add an inclusive parent total to the same children's totals. Record cached input separately when available and label estimated subscription consumption as estimated. The earlier conversation's fixed 2.5-times-activity shortcut is not a valid general break-even rule: different execution plans need not consume the same input/output mix, cache behavior, or total work. Public usage guidance describes multiple contributing factors, not a fixed cost per completed task. [W2, W4]

### 3.3 Select at the task-specific frontier

First reject unavailable, unauthorized, inadequate, or insufficiently verifiable plans. Then compare the remaining plans by quality, lifecycle cost, and integrated completion time. Remove dominated plans.

For an upgrade from plan `a` to `b`, the conceptual test is:

```text
material quality gain
+ expected repair avoided
+ useful earlier completion
> incremental cognition, context, coordination, and verification cost
```

These terms require explicit preferences or separately reported tradeoffs before reducing them to one number. Initially use reasoned categories and conservative ranges, not invented probabilities or a decorative weighted score.

Favor the stronger established route when the decision hinges on uncertain quality equivalence. Favor the simpler execution topology when uncertain coordination benefits are the only reason to split. Neither rule implies that the most expensive option is always best.

When evidence shows a plateau, use the cheaper equivalent route. When the next stronger configuration reliably improves a material dimension enough to pay for itself, use it even when the weaker configuration usually finishes.

Qualification attaches to the task envelope, verifier, and backend combination, not globally to a model or a loose label such as "adapter work." A familiar task with a new concurrency assumption is outside its old qualification. Worker self-confidence is a proposed assessment, not evidence of competence. When available checks cannot reveal the relevant semantic mistakes, retain the stronger owner or improve the evidence path before delegating.

**There is no universal model/effort ladder.** More effort on one model and a different model at less effort are different candidates. Higher effort is not a guarantee of improvement, and missing information cannot be supplied by extra reasoning. [W2]

## 4. Cost-aware, not scarcity-driven

The normal routing policy does not use remaining allowance, proximity to reset, or an unused reserve as a reason to lower quality or spend extravagantly.

A useful invariant is:

```text
same task + same evidence + same available capabilities + same preferences
=> same recommended execution policy
```

Changing only an account balance from comfortable to nearly depleted must not alter that recommendation. A reset must not make the same task suddenly deserve speculative reviewers.

Provider rejection is different from optimization. If a required capability becomes unavailable, Projector must preserve a resumable state and either use an already-qualified alternative or pause. It must not quietly relabel a weaker replacement as equivalent.

### Optional manual control: finish less, not worse

A manually enabled conservation policy may restrict new work admission, postpone optional experiments, reduce duplicated worker context, or finish only the already-accepted coherent slice. Mandatory scope within an accepted completion contract and its evidence requirements remain unchanged.

Any scope reduction must be recorded as deferred work, not disappear from acceptance criteria. A hard user spending cap stops or checkpoints work that cannot be completed within the cap at the required quality.

There is no automatic quality downgrade, no automatic API-billing fallback, and no instruction to consume an expiring allowance merely because it exists. A provider's own fallback behavior must be checked by the adapter rather than assumed absent.

The initial implementation needs checkpointing and explicit work admission, not a sophisticated conservation subsystem. Leave that subsystem unbuilt until a real manual use case justifies it.

## 5. Keep intelligence with the unresolved decisions

Astra / High remains the initial owner for Projector's current convergence work. This is a design judgment based on the workload described in the conversation, not a benchmark claim about the unseen wrap-up file.

The owner performs real implementation as well as integration. It is not a ceremonial manager that writes a lengthy plan, sends all meaningful work elsewhere, then rewrites the results.

Maintain responsibility over a **coherence region**: related work sharing active assumptions, contracts, and debugging state. Preserve that context across the region. Split only when the context that must be transferred is compact enough and stable enough to justify the transfer.

A phase-level label provides a default, not a cage. A settled phase can contain a six-line high-risk change. A difficult phase can contain a large mechanically specified adapter. Route at coherent capsule boundaries, not every tool call and not only once for an entire project.

### Stability without model babysitting

Hold the route while the capsule's basis remains valid. Reconsider on a material event: a new contract ambiguity, unexpected shared dependency, failed diagnostic hypothesis, invalidated verification assumption, or a demonstrated task-family alternative.

Escalate promptly on material risk. De-escalate only at a stable boundary with evidence that the lower route preserves quality. Do not oscillate after each passing or failing test.

## 6. Cheap work must be made bounded, not merely called easy

Before delegating to a lighter model, establish a **delegation envelope** within the existing Execution Capsule:

| Envelope element | Required meaning |
|---|---|
| Objective | Observable result and non-goals |
| State basis | Base revision plus relevant contract, semantic-state, and fixture digests |
| Context | Relevant source/decision references, negative constraints, and known uncertainty |
| Authority | What the worker may decide, and what it must return unresolved |
| Read and write scopes | Expected semantic and filesystem footprints |
| Effects | Allowed commands, services, generated outputs, and external interactions |
| Verification | Obligation-specific checks and independent evidence path |
| Return contract | Changed artifacts, evidence references, assumptions, and blockers |
| Stop condition | Specific discoveries that invalidate the envelope |

Do not create a new parallel specification. The envelope is a projection of accepted semantic state and policy.

A lower-tier worker can propose a patch, extract candidates, or generate fixtures. It cannot quietly broaden write scope, settle an architectural dispute, modify acceptance expectations to match its output, or suppress anomalies.

### Good starting uses for Luna

Use Luna initially for source-grounded extraction, structured inventories, locating potential references, grouping already-captured failures, and candidate fixtures under explicit behavior. Every meaningful claim carries a source locator; unsupported inference is labeled.

Even read-only work is not harmless by definition. An incomplete inventory can hide a required change. Where coverage matters, use deterministic enumeration as the coverage baseline and let the model annotate it. A model's list alone is not evidence that no omitted cases exist.

Read-only evidence also needs a coherent snapshot. Prefer an immutable revision or materialized snapshot. A child reading the owner's actively changing checkout cannot claim snapshot consistency merely by naming its starting commit. Without snapshot isolation, record actual read dependencies and detect intervening changes; reject or refresh claims whose basis is uncertain. Tests that write caches, fixtures, or services are effectful jobs even when the model only reports their results.

Allow code-writing only after a task family demonstrates the required quality with independent checks and low review burden. Small size alone does not qualify a task.

### Codex-Spark as an optional specialist

The separately limited model the user recalls is plausibly **GPT-5.3-Codex-Spark**, not GPT-5.4. Its published preview has a separate rate limit, and current model documentation still lists it. [W1, W3]

Consider it for narrowly specified edits where latency is valuable and its complete verification path qualifies. Do not use it for architectural arbitration merely to access another allowance. OpenAI's launch description says its lightweight default does not automatically run tests unless asked, so Projector must own test execution and acceptance rather than rely on model habits. [W3]

### Sol / XHigh and Terra are not prohibited

Their omission from the initial hot path is a simplification, not a claim of inferiority. Admit either when matched task-family evidence shows it occupies a useful quality/cost point. Do not permanently delete a candidate based on intuition alone.

## 7. Escalate the failure class, not the retry counter

A generic rule such as "after two failures, increase effort" wastes work and misdiagnoses missing evidence as inadequate intelligence.

| What failed? | Better response |
|---|---|
| Missing repository evidence or an incomplete capsule | Retrieve the missing evidence; repair the envelope |
| Unavailable tool, environment, dependency, or permission | Repair or report the execution precondition |
| Local implementation mistake with a clear cause | One focused repair inside the established route |
| Contradictory requirements or disputed contract | Strong owner resolves the smallest decision frontier |
| Several live hypotheses and a costly wrong answer | Focused Astra / XHigh investigation or discriminating experiment |
| New cross-worker coupling | Pause dependent writers; serialize or rebuild affected boundaries |
| Verification cannot distinguish right from wrong | Improve the oracle, not just the candidate answer |
| Repeated edits without new evidence | Stop the repair loop; change the diagnostic strategy |

Escalation requires a question to answer or evidence to obtain. "Think harder" is not an execution contract.

A repeated failure signature without new evidence is a stop signal even before a numeric retry limit. Investigation also has a bounded search scope and an explicit checkpoint outcome. An unresolved case remains unresolved; a limit does not transform it into success.

## 8. Parallelism is an investment decision

Do not optimize worker occupancy. Optimize accepted progress along the integrated critical path.

A proposed split must pass both tests:

1. **Semantic admissibility:** workers can proceed without incompatible decisions or uncontrolled effects.
2. **Economic usefulness:** the split improves quality or completion time enough to justify additional work, review, and integration.

A worktree supplies filesystem separation, not semantic independence. Codex documents separate checkouts and shared Git metadata; it also notes per-worktree dependencies and caches. [W7] Treat stateful services, databases, ports, test fixtures, and deployment targets as separately managed resources.

### 8.1 Build on Projector's semantic graph

Reuse the accepted execution DAG, Relevance Closure, Impact Closure, contract relationships, and uncertainty frontier. Do not infer independence only from disjoint file names. [P1, P2]

For each ready unit, derive:

```text
semantic reads and writes
contract dependencies and volatility
filesystem and generated-output effects
shared resource requirements
verification closure
context overlap with the owner and other workers
critical-path contribution
integration readiness
```

Two tasks can touch different packages yet change the meaning of the same serialization format. Conversely, shared reads of an immutable, accepted contract need not block concurrency.

Unresolved shared assumptions are a reason to discover the boundary first. Strongly coupled units should remain under one owner until a useful seam exists. Do not solve partitioning as an elaborate global optimization problem on every turn: compare a small set of coherent candidate partitions.

### 8.2 Select a topology, not just a worker count

| Topology | When it earns its cost |
|---|---|
| Owner stays local and sequential | Shared assumptions, small task, warm context, high integration cost |
| Read-only delegated investigation | A separable question benefits from independent attention or protects owner context |
| Deterministic parallel processes | Independent tests or transforms with isolated outputs |
| Sequential specialist | Bounded skill/cost advantage without a useful concurrency advantage |
| Parallel isolated writers | Stable contracts, bounded effects, meaningful independent work, affordable integration |
| Temporary independent candidate | A consequential disputed solution needs comparison; no automatic fan-out |

A fresh agent need not imply a new worktree. A worktree need not imply simultaneous execution. A different model need not imply either one.

### 8.3 Estimate actual benefit

Use a resource-constrained schedule, not `sum(task times) / number of agents`:

```text
parallel completion = setup
                    + constrained worker schedule
                    + integration queue
                    + reconciliation and required validation
                    + expected repair
```

Add duplicate cognition and review to resource cost. Measure the end of integration, not the time a child reports done.

Illustrative estimates, not Codex measurements: two independent 20-minute tasks with 3 minutes of setup and 5 minutes of integration yield a 28-minute parallel path instead of a 40-minute sequential path, before any additional contention. Two 5-minute tasks with the same overhead yield 13 minutes instead of 10. The second split is a loss before counting extra model usage.

A positive estimate is not enough when its uncertainty is larger than the proposed benefit. Require a material margin or use the simpler topology. Pure speedups that consume appreciably more resources need an explicit, stable speed preference; spare quota is not that preference.

### 8.4 Bound work in progress by integration capacity

Initially permit one additional isolated writer only when it qualifies. This is a conservative deployment default, not a permanent cap. Increase width when observations show meaningful benefit without growing an integration queue or defect load.

Do not launch another writer when the owner cannot review and integrate its likely output, when model-provider rate limiting cancels the expected speedup, or when local CPU/RAM/service contention makes execution counterproductive.

Re-evaluate width on actual integration events and newly discovered dependencies. Avoid waiting for a whole wave when one completed branch can safely integrate and unblock useful work.

## 9. Transactional integration, not merge-and-hope

Each writing capsule binds to its relevant input state. When that state changes, invalidate the dependent claims and work, not automatically the whole branch or whole repository.

The integration sequence is:

```text
finish local work and capture evidence
→ stop the worker's writes
→ validate actual effects against its envelope
→ compare relevant read/contract basis with current canonical state
→ stage the candidate combined revision
→ run affected integration and semantic checks
→ publish through the single integration authority
→ record accepted evidence and remaining obligations
```

A clean Git merge is not a semantic validity check. When a shared contract changes, downstream candidates cannot retain acceptance merely because their patches apply.

Shared contracts, root manifests, lockfiles, central migrations, generated registries, and CI configuration need deliberate ownership or serialization. Workers return requested shared changes to the coordinator rather than independently improvising them.

Worktree isolation is not a security boundary. Enforce approved commands and effects through the actual host sandbox and resource controls. A post-run diff can reject an out-of-scope patch, but it cannot undo an external side effect. Default worker access excludes canonical publishing and unapproved external mutation.

Cancellation must stop and acknowledge termination of the actual child process tree before releasing ownership. Preserve patches and diagnostics. Never discard user changes or an unintegrated worktree automatically.

Apply the same admission and lifecycle controls to native subagents, exec workers, and any descendants. Nested delegation is disabled initially; a worker cannot create unregistered grandchildren through shell commands. A client-local agent limit alone is not a global concurrency guarantee. If the available host cannot enforce a required boundary, mark that launch path unqualified rather than pretending instructions enforce it.

Materialize each worker's required instructions, accepted decisions, fixtures, and environment explicitly. Gitignored local plans and setup files are not guaranteed to exist in a new checkout. Do not bulk-copy credentials or mutable runtime state as a convenience. Record the environment fingerprint relevant to reproducibility, and give effectful tests isolated scratch space and service instances.

## 10. Context economy without information loss

The cheapest token is one that does not need to be generated or reread. But a short capsule that omits a governing constraint is not efficient.

Keep durable, referenced decisions and narrow evidence packets. Distinguish negative constraints, unresolved questions, and conflicting evidence rather than summarizing them into false certainty. Retain raw sources behind locators so the worker can inspect them.

Use context locality deliberately: keep tightly related work in the same owner; delegate noisy independent scans; avoid full-history forks for simple bounded jobs. Actual cache reuse and context behavior must be measured, not assumed.

A worker summary is a navigational aid, not a new authority. The integrator should inspect the evidence relevant to risk rather than reread every source blindly or trust a polished summary blindly.

Persistent ownership does not require an indefinitely growing chat transcript. When compaction, stale assumptions, or noisy context undermine the current working representation, refresh the owner from a state-bound capsule and referenced evidence. Preserve decisions and obligations, not conversational sediment. Compare this refresh cost with continued context reuse rather than imposing a reset every arbitrary number of turns.

There is no unconditional benefit to a strong model plus cheaper workers. If handoff production, lost context, or review costs more than completing the unit with the warm owner, keep the work local.

## 11. Verification is allocated with cognition

Choose `(worker, effort, verifier, topology)` as a package. Never choose a cheap worker first and discover afterward that only a complete expensive rewrite can establish confidence.

Use deterministic checks for deterministic obligations. Use independent, source-grounded review for semantic omissions, architectural distortion, and behavior that fixtures do not adequately constrain.

The worker may contribute tests, but those tests do not exclusively define correctness. Preserve causal origins: approved requirements, historical behavior, independent fixtures, and candidate-generated expectations are different evidence lanes. [P1]

A second instance of the same model is not automatically an independent oracle. Give the reviewer governing requirements and actual artifacts; withhold the writer's persuasive rationale initially where it could anchor the review. Cross-model review is optional, not inherently superior.

### Bounded adversarial loop

For a material change:

```text
attack specific obligations with counterexamples
→ classify findings and attach evidence
→ fix concrete defects or explicitly reject unsupported findings
→ rerun affected checks
→ attack changed assumptions and remaining risks
```

Stop when mandatory checks pass, blocking findings are resolved, and the final review identifies no new material issue within its tested scope. Do not call the result a proof of perfection.

Routine units need proportionate checks, not a mandatory multi-model committee. Kernel changes justify stronger independent review before integration. Review cost belongs to the route that made it necessary.

## 12. Learn which routes deserve trust

Start with understandable rules and telemetry. Do not begin with a model that invents precise success probabilities or a learned router that explores on valuable production work.

An outcome record should link:

- work and task-family identity, policy version, difficulty evidence, and relevant state;
- requested and host-reported model/effort, backend, client version, authentication class;
- context footprint, available token/cost measurements, and measurement confidence;
- topology, setup cost, resource contention, and integration latency;
- quality findings, repair cycles, user corrections, and eventual acceptance;
- later attributable regressions, changed assumptions, and unresolved exposure.

Record structured conclusions and evidence references, not private chain-of-thought traces.

### Guard against misleading success

A route is not good because it passes its own tests, produces fewer reported findings, or finishes its local task quickly. Track escaped defects, omitted impact, integration rewrites, maintainability regressions, and human intervention.

Attribute later repair when evidence supports the relationship, and mark ambiguous attribution rather than force a label. Use fixed follow-up windows plus reopening of outcomes when a later defect is linked. Unknown future cost is not zero.

Task routing creates selection bias: the cheaper model may have received only easy tasks. Compare matched task families and fixture difficulty, not global model averages.

### Evaluation and promotion

Establish a baseline of a competent single Astra / High owner with the same bounded-context and verification improvements. Otherwise routing receives credit for improvements that came from better task specification.

Compare against: fixed Sol / High where appropriate; Astra / XHigh on selected hard units; native delegation; exec-based delegation; and alternative widths for genuinely independent writers. Do not run every permutation.

Use replayable Projector-relevant changes, including contract ambiguity, invalidation, recovery, authority conflicts, analyzer adapters, and integration-only failures. Hold out fixtures, include adversarial negatives, repeat enough cases to characterize variability, and separate tuning from evaluation.

A cheaper route is promoted only when predefined material quality margins are met and lifecycle economics improve. A stronger route is promoted when its added quality earns its cost. Unknown or sparse evidence retains the stronger established route for consequential work.

Capability profiles expire when relevant model versions, prompts, tools, task families, or contracts materially change. Learned selection proposes; deterministic admission constraints still govern.

## 13. Make successful reasoning reusable

The highest-leverage saving is not repeatedly choosing between models. It is converting repeated uncertainty into reusable executable knowledge.

When a class of errors recurs, ask whether the retained resolution can become:

```text
a deterministic recognizer
an explicit contract or ownership rule
an impact selector
an independent fixture or metamorphic check
an integration precondition
an evidence-backed task-family route
```

This is consistent with the supplied semantic-holon proposal's crystallization of cognition into senses and validators. [P1] The compute policy should benefit from that knowledge without requiring a holon implementation or a trained persistent system conception first. [P4]

New learned rules and validators begin as proposals, not authority. Promote them through governed review, historical and negative-case replay, and independent evidence. Preserve their scope and invalidate them when their basis changes. Otherwise a mistaken repair can become an efficient machine for repeating the mistake.

Measure the marginal cost of repeated changes after learning. A one-off expensive investigation may be economical if it removes a recurring uncertainty, but claimed future savings must be tested rather than used to justify any speculative framework.

## 14. Small implementation surface

Implement this as policy inside the existing planner, capsule compiler, execution adapter, evidence recorder, and integrator. Reuse their identities and state contracts. Avoid a new package per noun or a second graph store.

The minimal additional records are projections or attachments, not necessarily new canonical entities:

```text
ExecutionPolicyDecision
  chosen route + alternatives rejected + evidence + validity basis

BackendCapabilityRecord
  available models/efforts + launch paths + observed guarantees

ExecutionOutcome
  actual route + lifecycle resources + quality and follow-up evidence
```

The first working path should use a small deterministic decision function with an explicit owner-judgment escape hatch. The strong owner resolves exceptional classification using already-required task reasoning. No new router model call is mandatory for ordinary work.

Do not let candidates alter the router, loosen their own permissions, or edit acceptance checks merely to get accepted. Changes to execution policy and evaluator policy are themselves governed changes.

## 15. Policy algorithm

The following is design pseudocode, not an existing Projector API:

```text
allocate(case, current_state, policy, capability_registry):
    preserve the accepted completion contract
    derive affected semantic closure and outstanding uncertainty

    execute independently valid deterministic portions with required checks
    if they complete the accepted scope:
        return the validated outcome
    retain unresolved work and any failed preconditions explicitly

    form a small set of coherent candidate units and topologies
    include the current qualified owner as the baseline

    for each candidate plan:
        check model, effort, authentication, permissions, and host support
        check semantic ownership and external-effect constraints
        check the independent verification path
        estimate quality, total resources, integrated time, and uncertainty

    reject candidates that cannot preserve required quality
    reject unsupported independence and uneconomic delegation
    retain a simple, strong baseline when evidence is inconclusive
    choose the material quality/cost frontier point

    bind the route to current relevant state and the policy version
    execute under enforceable limits
    reconcile actual effects and validate the combined result
    record acceptance, rejection, and downstream learning

    on a material basis change:
        pause affected work, repair the envelope, and reallocate locally
```

`remaining_quota` and `time_until_reset` are absent from normal ranking. `capability_unavailable` and an explicit user-set admission cap can prevent execution; they cannot authorize a weaker quality contract.

## 16. Codex feasibility and limits, checked September 11, 2026

### Verified public capabilities

Current official model documentation lists `gpt-6-astra`, `gpt-5.6-sol`, `gpt-5.6-terra`, `gpt-5.6-luna`, and `gpt-5.3-codex-spark`. Its examples also retain some shorter aliases. Resolve installed-client model identifiers rather than assuming aliases behave identically everywhere. [W1]

Current subagent documentation supports custom model and reasoning settings. It says unset child settings can inherit the parent, while selecting a model without an effort can use the chosen model's default. Therefore a policy must bind both where supported, instead of relying on accidental inheritance. [W5]

`codex exec` is a documented automation path with explicit model selection, sandbox settings, JSONL events, structured final output, and saved-auth reuse. It is a backend option, not an entitlement workaround. [W6, W8]

GPT-5.4 and GPT-5.4 mini were retired from ChatGPT-authenticated Codex on **August 31, 2026**. The announced replacements are Terra and Luna. This change does not apply to API-key use. [W4]

Luna Reserve is a separate, conditional allowance for selected accounts after regular usage is exhausted. It is not another model, not generally an always-available parallel budget, and the public description does not establish native-child or exec access to it. [W9]

### What is not established here

Native-child Spark support on the user's installed build; exact supported Spark efforts; reserve access through children or exec; account-specific pool accounting; actual runtime model telemetry; reliable sandbox enforcement in that environment; and any measured performance advantage for this routing design remain unverified.

The current configuration reference and model/subagent guidance expose somewhat different effort descriptions. Treat the installed client and its supported model metadata as the operational contract. Do not copy a global list of efforts onto every model. [W1, W5, W8]

### Backend qualification probe

At setup, and after relevant upgrades, the adapter should perform a bounded read-only probe for each enabled route:

1. Discover client version, accepted model identifiers, supported efforts, and explicit authentication mode without dumping credentials.
2. Launch the requested native child or exec process with a known harmless packet.
3. Capture host-reported resolved settings and any available usage/pool metadata.
4. Check unsupported model/effort behavior, cancellation, timeout, output parsing, working directory, and permission boundaries.
5. Store supported, unsupported, or unknown for each guarantee.

Model prose such as "I am Astra" is not attestation. Record the provenance and limits of host metadata; a launch request is not proof of the model actually used. Where silent downgrade cannot be detected or prevented, do not use that path for quality-critical autonomous writes.

A successful setup probe is not a permanent guarantee. Bind each run to its resolved capability record; detect material runtime setting changes where the host exposes them. If a fallback or model change occurs, suspend further mutative actions and requalify the route. Quarantine any output produced under an uncertain binding. A backend unable to provide the required no-silent-downgrade guarantee remains ineligible for that class of autonomous work.

Try native subagents first when they meet the required controls. Use an exec adapter when it gives clearer launch, lifecycle, or worktree control. Both must satisfy the same quality policy. Launching another CLI does not grant a model that the account cannot use, switch billing modes safely without authorization, or manufacture a separate allowance.

### Initial owner setting

The documented identifiers support this starting configuration, subject to the installed client's verification:

```toml
model = "gpt-6-astra"
model_reasoning_effort = "high"
```

This is a recommendation, not a change made to the user's configuration. Do not automatically inherit these settings for every leaf worker.

## 17. Acceptance scenarios for the policy itself

| Scenario | Required behavior |
|---|---|
| Identical available capabilities, different remaining allowance | Same normal recommendation and same quality contract |
| Lower model available only after fallback | Use only if already qualified for the task; otherwise checkpoint |
| Cheap worker passes its own wrong tests | Independent obligation check rejects the result |
| Two branches touch disjoint files but disagree on a contract | Reject parallel independence or invalidate affected work |
| Shared contract changes while children run | Pause/rebind affected capsules; no stale acceptance |
| Parallel work is faster locally but slower to integrate | Account for integration time and reject the false speedup |
| Owner must rewrite a cheap worker's output | Charge rewrite and review to that route's lifecycle outcome |
| Same failure repeats without new evidence | Stop local repair and change diagnostic strategy |
| Missing source evidence is mistaken for low intelligence | Retrieve evidence before purchasing additional reasoning |
| Out-of-scope filesystem change | Quarantine result; do not merge it automatically |
| Unauthorized external effect requested | Enforce denial before execution, not only after diff review |
| Native child silently resolves to another model | Reject that route's claimed qualification or pause writes |
| Provider rate limit or child crash | Preserve resumable state; no quota-driven lowering of standards |
| Cancellation while child still writes | Retain ownership until termination is confirmed |
| Small mechanical task with a warm owner | No mandatory delegation, worktree, or review committee |
| Separate-pool model has worse total repair economics | Reject despite lower main-pool consumption |
| A useful independent task benefits from specialization but not concurrency | Use sequential delegation if its full cost qualifies |
| Policy has few observations for a consequential task family | Do not manufacture confidence or explore on canonical state |
| Agent attempts to relax the evaluator | Treat as governed policy change, not ordinary task repair |
| Later regression is linked to an accepted result | Reopen outcome and update route evidence |
| Read-only child scans a checkout during concurrent mutation | Require a coherent snapshot or invalidate affected evidence |
| Worker spawns another exec process outside admission control | Deny unregistered delegation; do not trust only a local agent cap |
| Required plan exists only in an ignored local folder | Materialize approved inputs explicitly before launching |
| A proposed learned validator encodes a mistaken repair | Withhold authority pending independent promotion checks |
| Parent usage totals already include child usage | Deduplicate by lineage instead of counting it twice |
| Familiar task label hides a new concurrency assumption | Requalify the envelope; do not inherit a blanket cheap-model license |
| Model changes after a successful setup probe | Suspend writes and requalify; do not trust the earlier binding |
| Long-lived owner context becomes stale or noisy | Refresh from current authoritative state without losing obligations |

These are requirements for future implementation tests. They were not run against a live Projector scheduler in this conversation.

## 18. Build sequence and deletion criteria

### Slice A: transparent baseline

Keep Astra / High as the owner. Add compact lifecycle telemetry and the ability to record an execution-policy decision without delegation. Preserve a strong single-owner baseline.

### Slice B: one qualified leaf route

Choose a repeatable task family with independent checks. Compare owner execution with a Luna or Sol delegate using the same contract and fixtures. Verify the actual backend route. Enable only when quality and lifecycle cost support it.

### Slice C: one genuine parallel seam

Choose two complete units behind an accepted stable interface. Add one isolated writer, explicit shared-resource ownership, state-bound integration, cancellation, and outcome accounting. Compare integrated completion against sequential execution.

### Slice D: focused escalation and retained learning

Add bounded Astra / XHigh consultation where additional reasoning or independent challenge resolves a material problem. Cache valid decisions and convert repeated findings into deterministic checks.

### Slice E: optional candidate expansion

Evaluate Spark, Terra, alternative efforts, and wider execution only where observed workloads justify them. A learned statistical router comes later, if simple policy is leaving measurable value on the table.

Each slice should produce useful functionality independently. Do not postpone actual Projector work until a generalized scheduler, neural policy, or multi-model benchmark system is complete.

Delete or disable a route when its quality or full lifecycle economics do not beat the relevant baseline. If the routing machinery costs more than it saves, keep the simpler ownership and verification improvements and remove the machinery.

## 19. Final operating constitution

> Keep the strongest justified owner on unresolved semantics. Delegate only bounded work with a credible independent acceptance path. Parallelize only when semantic independence and lifecycle economics both support it. Learn from integrated outcomes, not task-completion theater. Turn repeated reasoning into durable executable knowledge. When resources are exhausted, preserve good work rather than manufacture lower-quality progress.
