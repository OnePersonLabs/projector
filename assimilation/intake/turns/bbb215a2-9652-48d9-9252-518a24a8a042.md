## Assistant

Exactly. Taken to the limit, **software becomes a model-mediated control system**, and source code becomes one optimization artifact among several.

The cleanest formulation I can see is:

\[
\boxed{\text{Program} = \text{persistent model state} + \text{tools} + \text{constraints} + \text{rendered execution artifacts}}
\]

Code then exists because silicon, browsers, databases, GPUs, cloud APIs, operating systems, and networks still reward certain deterministic representations.

So instead of:

\[
\text{requirements} \rightarrow \text{code} \rightarrow \text{runtime}
\]

you get:

\[
S \rightarrow
\begin{cases}
\text{compiled/generated code} \\
\text{runtime submodels} \\
\text{tool calls} \\
\text{UI projections} \\
\text{queries} \\
\text{temporary scripts}
\end{cases}
\rightarrow \text{effects}
\]

That is a much more general computer.

## The spectrum matters

I think there are at least four interesting points on it.

| Level | Canonical thing | What code becomes |
|---|---|---|
| 0 | code | everything |
| 1 | S + code | implementation generated/repaired from S |
| 2 | S + generated components | code is cached materialization |
| 3 | S + specialized submodels + tools | deterministic code only where advantageous |
| 4 | persistent executable model | code is ephemeral actuator glue |

Level 4 is your extreme case:

> The application **is** the model.

It maintains state, understands its purpose, talks to users, decides what interaction surface should exist, and synthesizes whatever deterministic machinery it needs.

A browser app might literally have a persistent semantic core saying, approximately:

> I am a collaborative music-learning environment. Here is the current user state, product intent, interaction model, visual language, skill ontology, and capability set.

Then depending on what happens it could:

- generate DOM/UI structures
- call WebAudio
- synthesize a WebGL visualization
- create a temporary state machine
- generate SQL
- instantiate a small deterministic worker
- produce a shader
- ask another model for a specialized operation
- discard all of it afterward

The generated artifacts are **muscle contractions**, not identity.

## This also changes what “UI” is

Today:

\[
\text{state} \rightarrow \text{prewritten components}
\]

Your model-native version could be:

\[
(S,\ user,\ current\ state,\ intent)
\rightarrow \text{interaction surface}
\]

So the application isn't choosing among screens.

It's continuously deciding:

> What is the most useful interface projection of myself for this human, right now?

That could still produce ordinary React/HTML underneath because browsers are excellent rendering machinery.

But React becomes something closer to **machine code for UX**.

The app's semantic identity sits above it.

But those are pieces. I don't see the whole conception we're constructing represented there.

## The really important inversion

I think we should stop thinking:

> “How much code can AI generate?”

and instead ask:

> **What portions of computation actually deserve to be frozen into code?**

That is a better question.

Code has some astonishing properties:

- near-zero marginal inference cost
- deterministic behavior
- extremely low latency
- easy replication
- formal analysis
- precise resource utilization
- excellent hardware mapping

So you'd “crystallize” behavior into code where those properties matter.

Everything else could remain **fluid**.

This gives you a beautiful architecture:

### Fluid semantic layer

Model-native.

Handles:

- interpretation
- adaptation
- planning
- personalized behavior
- ambiguous decisions
- evolving UX
- semantic state
- reasoning

### Crystalline execution layer

Generated or maintained artifacts.

Handles:

- hot loops
- protocols
- schemas
- realtime audio
- rendering kernels
- security boundaries
- transactions
- reproducible computation

The system could even migrate behavior between the two.

If some operation starts fluid but gets performed constantly:

\[
\text{model behavior}
\rightarrow
\text{observed stable pattern}
\rightarrow
\text{synthesize implementation}
\rightarrow
\text{verify}
\rightarrow
\text{cache/crystallize}
\]

And if assumptions change:

\[
\text{code}
\rightarrow
\text{invalidate}
\rightarrow
\text{return responsibility to model}
\rightarrow
\text{re-crystallize}
\]

Now software has a kind of **adaptive compilation boundary**.

That feels genuinely new.

## And specialized submodels fit perfectly

A sufficiently complex \(S\) might spawn smaller models:

\[
S
\rightarrow
\{M_{ui},M_{domain},M_{planner},M_{audio},M_{user}\}
\]

These aren't generic agents with prose instructions.

They could be **projections/distillations of the parent system conception** optimized for specific responsibilities.

Your NeRF analogy comes back here beautifully.

A scene representation can be sampled from different viewpoints.

Likewise:

\[
M_i = P_i(S)
\]

where \(P_i\) produces a model specialized for a region of semantic space.

The UI model knows exactly the interaction worldview.

The domain model embodies product semantics.

The realtime model knows narrow timing behavior.

The big frontier model can still be summoned when genuinely novel reasoning is required.

## Which produces an absolutely bonkers deployment model

Imagine shipping:

psychord/

    materialized/
        audio-worklet.wasm
        storage-schema.sql
        midi-driver.ts

At runtime the application is partially static and partially *alive*.

Its static parts are cached conclusions.

Its model parts retain the capability to reinterpret intent.

And source code stops occupying the privileged status it currently has.

## There's a philosophical boundary worth preserving

I would resist saying:

> everything should become neural.

The deeper insight is not “neural good, code obsolete.”

It's:

> **Representation should match epistemic character.**

Stable, precisely known relation?

Use deterministic machinery.

Fuzzy, contextual, evolving relation?

Keep it semantic/model-native.

Today we force almost **everything** across the second-to-first boundary because code is historically the only executable substrate we've had.

We take:

> “Make this interaction feel appropriate.”

and somehow force it through:

```typescript
if (isMobile && user.hasCompletedOnboarding && ...)
```

😂

Of course software becomes enormous.

We're compiling meaning into brittle finite machinery far earlier than necessary.

## This loops directly back into Projector

Projector could ultimately be less a development tool and more a **compiler/runtime for semantic software**.

Its responsibilities become:

1. Maintain \(S\).
2. Harden and update \(S\).
3. Decide what should remain model-native.
4. Decide what should crystallize into deterministic artifacts.
5. Generate those artifacts.
6. Validate that they remain faithful projections.
7. Invalidate/regenerate them as \(S\) changes.
8. Produce specialized submodels when semantic regions deserve their own runtime.

Then the extraordinary end-state is:

\[
\boxed{\text{Software development becomes model development.}}
\]

Not “train an LLM to write an app.”

Develop the **computational conception of the app**, and let the machine continually choose appropriate representations for executing it.
