## Assistant

**Yes. Your metaphor describes a compelling *product experience* for Projector—but the important breakthrough is not the swarm. It is the targeting solution.**

You are describing a system that does the difficult understanding and design work, then **compiles that understanding into a precise, bounded program for changing the repository**.

The satellites execute that program. They do not each descend onto the planet, wander around, invent their own interpretation of the mission, and start moving buildings.

That is a much sharper ambition than “an agent with good memory, planning skills, and subagents.”

## How this compares with Projector as it exists

I inspected the current `main`, including its retained requirements and planning code. **There is substantial alignment already—but having the machinery’s components is not the same as delivering the whole experience.**

| Layer | What I found in Projector |
|---|---|
| **Durable project understanding** | Accepted meaning, architectural decisions and reasons, pre-edit context retrieval, and reconciliation of retained knowledge against changes are part of the documented product surface.  |
| **Bounded execution machinery** | Concrete engine code constructs immutable execution plans and worker capsules containing relevant requirements, decisions, allowed and forbidden writes, unknowns, and completion obligations.  |
| **Transformation planning** | Internal code compiles proposed packets into dependency-ordered work. The retained requirements specify semantic anchors, preconditions, exclusive claims, postconditions, and convergence—but explicitly mark the complete public composition workflow as unrealized.   |
| **The complete orbital-swarm experience** | The README explicitly says general autonomous repair selection, modernization, and multi-packet orchestration are not established public workflows.  |

So my assessment is:

> **Your idea is not an alternative to Projector. It is a clearer definition of what Projector’s foundations should enable.**

There is a particularly revealing boundary in the code: `compileSemanticChangePlan` asks an injected `packets.compile(...)` provider to supply work proposals, then checks and packages those proposals. That module does not itself solve the central question: **“Which exact transformations constitute the correct change?”** Having a reliable container for a targeting solution is different from reliably deriving that solution. 

That is the seam I would investigate and strengthen first.

## The project owner and the construction fleet are different jobs

Your first paragraph is just as important as the orbital machinery.

The desired agent is not merely responsible for executing your instructions. It is responsible for **developing and maintaining an adequate understanding of what you are trying to accomplish**.

I would make the division of responsibility:

**You own what matters. The agent owns discovering, explaining, and maintaining a coherent way to realize it.**

That means the agent should resolve codebase-answerable questions itself, expose consequential tradeoffs with recommendations, notice when a requested implementation conflicts with the underlying goal, and remember why previous decisions were made.

Pocock’s current `grill-with-docs` is a useful adjacent mechanism: it combines interviewing with retained vocabulary and architectural decisions. But I would make that behavior part of the steward’s normal operating loop, not a special ceremony you must remember to invoke. citeturn504328search9

The important upgrade is **not endless grilling until every conceivable question has an answer**. It is:

> **Resolve the uncertainties that could change the next consequential commitment. Keep the rest explicitly provisional.**

Sometimes that requires an experiment or a throwaway implementation before the proposal can mature. The steward should own that discovery work too, rather than pretending conversation alone can settle everything.

And its continuity should reside in Projector’s durable model—not depend on keeping one increasingly enormous chat alive.

## What makes the orbital precision real

I would organize the execution side around an **executable change program**, rather than a prose task list.

A task list says:

> Replace the old implementation, update its consumers, and clean up the obsolete code.

A change program needs to answer:

> Which implementation? Which consumers? Under which observed state? What must remain unchanged? How do we know the obsolete path is actually gone?

For a hypothetical API migration, one instruction might amount to:

```text
Operation: migrate callers of InstrumentFactory.create
Targets:   resolved reference set Q, bound to snapshot S
Reads:     old/new contracts and reference-query membership
Writes:    resolved call nodes and required imports
Preserve:  the accepted InstrumentPort behavior
Reject:    ambiguous targets or invalidated assumptions
Verify:    compatibility checks and absence of old callers
```

That is still a human-readable rendering. Beneath it, the targets and checks must resolve to machine-addressable entities.

### The map must describe responsibilities, not just files

Your “sections precisely and concretely identified” should include symbols, declarations, configuration entries, generated outputs, registrations, and relationships—not merely folders or line ranges.

A capability may have a body spread across implementation, tests, schemas, configuration, and a frontend. Conversely, one file may embody several unrelated responsibilities.

This is where Projector’s meaning-to-implementation bindings should earn their keep. Its current pre-edit relevance requirement already calls for traversing canonical relations and implementation bindings, while distinguishing confirmed relevance from candidate interpretations and unknown frontiers. 

But **a dependency graph is not automatically a complete map of meaning**. A reference resolver can identify a call; it does not, by itself, establish every behavioral expectation surrounding that call.

The system must distinguish:

**“We resolved these targets exactly”** from **“We have established that these are all the relevant targets.”**

Those are different achievements.

### The operations should be mechanical wherever possible

For renames, structural moves, generated outputs, import rewrites, and supported API migrations, I would prefer executable transformations over asking a model to reproduce the edit repeatedly.

Type-aware refactoring already provides useful machinery here. For example, OpenRewrite’s lossless semantic trees combine type information with formatting preservation to support more precise matching and transformation. That is an ingredient—not the entire Projector solution. citeturn650311view0

For genuinely new behavior, use a model to synthesize a bounded implementation against established contracts.

**Do not require the model to improvise everything merely because some parts require creativity.**

The resulting division is:

> Reason about the design; synthesize the genuinely new parts; mechanically transform everything that has become well specified.

### The plan must bind what it read, not just what it edits

Here is a subtle but crucial case.

The planner determines that a deprecated interface has three consumers. While replacement code is being prepared, another change adds a fourth consumer.

None of the original three files changed. Their hashes still match. Nevertheless, the removal plan is stale.

Therefore, the plan must depend on **the result of the consumer query**, including membership and sometimes the absence of results—not merely the files it previously discovered.

Projector already retains exactly this requirement: scoped invalidation includes query results, empty queries, selector membership, and newly introduced consumers. That is genuinely relevant to your laser-targeting intuition. 

Bazel’s incremental model provides the useful underlying lesson: precise reuse and parallel evaluation depend on recording the actual inputs. Unregistered dependencies undermine those guarantees. citeturn650311view1

## I would change the order of your orbital operation

Not the spirit—just one important implementation detail.

**I would not destroy the old structures first. I would prepare and validate the replacement in a shadow repository state, then promote the coherent result.**

The internal sequence would usually resemble:

```text
Establish contracts and affected regions
                  ↓
Prepare replacements and mechanical rewrites
                  ↓
Compose them in a shadow tree
                  ↓
Validate the resulting system
                  ↓
Retire obsolete paths and verify their absence
                  ↓
Promote the validated repository state
```

Some changes require different internal ordering. The point is that the user experiences one coherent change, while the machinery handles intermediate states privately and deliberately.

For live databases or external services, repository promotion alone cannot make those side effects atomic; those need their own migration and recovery arrangements.

Your **“one progressive iterative pass”** is a good objective when interpreted as:

> **One coordinated evolution, with local iteration where evidence requires it—not repeated global rediscovery and replanning.**

A failed adapter test should not cause the whole fleet to forget the mission.

There is also a concrete mismatch to address in the current planner: its packet normalization rejects overlapping semantic ownership or write selectors between packets, even when dependencies order them. Your “remove, replace, then refactor this same region” therefore needs either **one compound packet owning that region throughout**, or a richer representation of deliberately ordered transformations with intermediate-state checks. Merely adding more workers would not solve that. 

## The satellites should mostly not be agents

This is the biggest leverage upgrade I see.

**Do not equate a satellite with an LLM. Equate it with an execution capability.**

Some capabilities would be model-driven: investigating an unfamiliar subsystem, resolving a design problem, or implementing genuinely new behavior. Others should be ordinary tools: semantic rewriters, generators, compilers, validators, dependency analyzers, and patch integrators.

The scheduler should dispatch independent work because the dependency and effect model permits it—not because “a swarm” sounds faster.

Even disjoint writes are insufficient by themselves. One worker can change a contract that another worker relied on while editing an entirely different file. The system needs to account for shared assumptions and read dependencies as well as write collisions.

Projector’s retained coordination policy already points in the right direction: parallel preparation and isolated worktrees, with coordinated final mutation of shared governed state. 

The payoff should come from eliminating repeated work:

- Workers do not independently reconstruct settled architecture.
- Mechanical edits do not consume fresh creative reasoning.
- Unrelated changes do not invalidate already justified work.

**Parallelism is an additional benefit. Avoiding repeated cognition is the deeper one.**

## Where near-determinism is realistic—and where it is not yet earned

I would separate three questions.

**Can we hit the selected target exactly?**  
For supported representations and transformations, this is an appropriate engineering objective: resolve the target, check the bound inputs, apply the operation, and reject mismatches.

**Can we know that the selected targets cover the whole change?**  
This depends on the quality and coverage of the semantic model, analyzers, runtime observations, and explicit boundaries. Unknown dependencies must remain visible rather than disappearing behind a confident plan.

**Can we know the proposed change realizes the right intention?**  
That requires the steward’s understanding work, meaningful acceptance criteria, experiments where needed, and evidence that can challenge the implementation—not merely confirm its own assumptions.

Your system should make the first question as mechanical as possible, progressively improve the second, and preserve intelligent scrutiny of the third.

**Deterministic execution of an incorrect plan is still an incorrect change.**

Fortunately, Projector’s current lens requirement makes an important distinction: handwritten implementations can vary while satisfying executable predicates; exact output is required only where a lens actually owns deterministic generation. That avoids forcing the entire project into “everything must be regenerated from a perfect specification.” 

The ambition should be **bounded uncertainty with precise execution**, not an unsupported claim that all software meaning has become decidable.

## What I would build next

I would **not** add another huge planning apparatus or a competing workflow store. The current repository explicitly favors its existing canonical model over reviving historical plans or adding a parallel `ChangeCase` store. 

I would connect and exercise the existing machinery through one demanding workflow:

> **Replace an implementation across package boundaries, preserve its public contract, add a new capability, migrate consumers, and remove the obsolete path.**

Make the example complex enough to expose the difference: include generated artifacts, configuration-based registration, and a consumer introduced between planning and execution.

The system should demonstrate that it can identify the intended edit regions, declare what it cannot establish, prepare independent work, detect the newly invalidated assumption, preserve still-valid work, and finish against acceptance checks established independently of the generated implementation.

Compare that with a strong ordinary agent using the same model and available tools. Measure **total completion cost, missed impacts, surprise edits, rework, and retained valid work**—including Projector’s initial indexing and modeling cost. Otherwise, the impressive orbital sequence could merely be hiding an expensive planning phase.

That would test your actual proposition, rather than demonstrating that five agents can perform five tasks.
