## Assistant

Yes. I’d make this a **first-class constitutional subsystem of Projector**. Not “be efficient” prose. Not a prompt hint. Something the orchestration machinery is required to consult before spending meaningful work.

The clean name I’d use is **Work Economics**.

Projector already has a progressive architecture principle: requirements activate concerns, and decisions happen only when those concerns become material. fileciteturn2file0 I’d extend that symmetry one level downward:

> **Material concerns do not automatically authorize work. They activate Work Economics, which determines whether the work is worth doing, when it should be done, how much evidence it deserves, and how much burn may be spent on it.**

That also generalizes the throughput ideas already developed around bounded context, delta-scoped review, critical-path scheduling, narrow verification, and avoiding ceremony. fileciteturn2file1

## The constitutional invariant

I would put something close to this into the authoritative spec:

> **Projector MUST seek to maximize marginal verified progress toward governing intent per unit of total development burn over the relevant planning horizon.**
>
> No non-trivial work is justified merely because it is useful, relevant, possible, requested by an internal concern, or likely to improve the system.
>
> Before materially expensive work is undertaken, Projector MUST establish proportionate evidence that its expected value, strategic timing, or information value justifies its expected burn and persistent burden.
>
> Evidence gathering itself is work and is subject to the same economic constraint.
>
> Once sufficient evidence exists to make the decision, Projector SHOULD stop gathering evidence.

That last pair is crucial. Otherwise we invent an accountant that eats more tokens than the workers. 🦑

### “Burn” is much bigger than tokens

I would explicitly model two vectors rather than a seductive single score:

| Expected return | Expected burn |
|---|---|
| direct user/requirement value | model tokens / quota |
| correctness improvement | wall-clock latency |
| risk reduction | retries / failed attempts |
| architectural coherence | orchestration overhead |
| future work eliminated | review burden |
| reusable capability | verification cost |
| downstream work unblocked | merge/integration cost |
| information gained | context reconstruction |
| option value preserved/created | implementation complexity |
| recurring future savings | permanent maintenance burden |
| uncertainty eliminated | coupling / migration residue |

Then **hard constraints filter first**, and a configurable policy ranks the survivors. This avoids turning Projector into a little spreadsheet demon maximizing `benefit / tokens` while quietly destroying architecture.

It also fits the viability-vector thinking already developed for semantic holons, where complexity and externalized burden must be accounted for instead of letting a locally useful improvement masquerade as a globally good one. fileciteturn2file2

## The actual control loop

I’d make this part of every `ChangeCase`:

```text
candidate work appears
        ↓
cheap materiality gate
        ↓
is this trivial / obvious / low-risk?
   yes ───────────────→ lightweight fast path
   no
        ↓
estimate return / burn / timing / uncertainty
        ↓
could more information materially change the decision?
   yes → acquire CHEAPEST decision-changing evidence
                 ↺
   no
        ↓
choose disposition
        ↓
skip | defer | bundle | probe | execute | escalate
        ↓
set bounded work budget + stopping conditions
        ↓
execute incrementally
        ↓
new evidence / checkpoint
        ↓
is next increment still economically justified?
        ↺ yes
        ↓ no
stop / settle / change strategy
        ↓
record actual outcome
        ↓
calibrate future estimates
```

There are several important consequences hidden in that little loop.

### **`defer` becomes a real decision, not procrastination**

A change can be worthwhile and still be wrong **now**.

Projector should understand things like:

```text
valuable after API X stabilizes
valuable when feature Y exists
valuable if this problem recurs twice more
valuable when three consumers can share it
valuable when the current migration completes
valuable if benchmark Z falls below threshold
```

So deferral should ideally carry an **activation predicate**, not merely “maybe later.”

That is strategically much stronger than a backlog.

### **`probe` becomes extremely important**

Before spending 200k tokens integrating some clever external architecture, Projector might spend 8k tokens answering the one question upon which the entire decision pivots.

This is essentially **value-of-information scheduling**:

> Find the cheapest experiment capable of flipping the decision.

That should become one of Projector's signature behaviors.

# Borg assimilation becomes much sharper

Every assimilation candidate should go through Work Economics.

And I’d introduce one particularly aggressive rule:

> **Assimilate value at the lowest permanent ontological weight that preserves the demonstrated advantage.**

Meaning an external project may contain:

```text
a whole subsystem
```

but what Projector actually needs might only be:

```text
an invariant
a scheduling heuristic
a graph relation
a validator
a deterministic transform
a test fixture
a learned policy prior
```

If stealing **one idea** gives 90% of the advantage while importing 3% of the maintenance surface, Borg should steal the idea.

Very Borg, actually. No obligation to preserve the victim's anatomy. 😈

So assimilation becomes:

```text
external capability
      ↓
what actual advantage might exist?
      ↓
what evidence would demonstrate that advantage?
      ↓
cheapest comparative probe
      ↓
no measurable advantage → discard

advantage exists
      ↓
what is the minimum native mechanism that captures it?
      ↓
concept / rule / sense / transform / subsystem
      ↓
shadow evaluation
      ↓
measured benefit > acquisition + permanent burden?
      ↓
assimilate
```

That would have been a fantastic formal lens for the `consensus-rnd` question you were asking earlier.

# This should govern *orchestration itself*

This is where it gets powerful.

Work Economics should be consulted for decisions like:

```text
Should I invoke a frontier model?
Should I launch another worker?
Should I research this uncertainty?
Should I reread more of the repo?
Should I perform an adversarial review?
Should I run the entire test suite?
Should I broaden Relevance Closure?
Should I refactor this while I'm here?
Should I parallelize this task?
Should I wait and batch three related changes?
Should I crystallize this learned behavior into deterministic machinery?
```

That means the system can progressively discover things like:

> “For this repository, independent second review of analyzer changes catches almost nothing and costs 18% of total burn.”

Reduce it.

Or:

> “Architecture-kernel changes have a nasty tail risk. Strong-model adversarial review costs 12% more but eliminates 61% of downstream rework.”

Spend it.

Or:

> “Frontier-model planning on these routine adapter tasks is wasted. This smaller model succeeds 98% of the time.”

Route accordingly.

Now quota conservation stops being a collection of hand-tuned tricks and starts becoming a **learned property of the development system**.

# Make it evidence-adaptive, but don't let it thrash

Each economically meaningful action should leave behind a tiny forecast/outcome pair:

```ts
interface WorkEconomicsAssessment {
  actionClass: ActionClass;

  expectedReturn: ReturnVector;
  expectedBurn: BurnVector;
  timing: TimingFactors;

  uncertainty: number;
  evidenceRefs: EvidenceRef[];
  assumptions: AssumptionRef[];

  disposition:
    | "skip"
    | "defer"
    | "bundle"
    | "probe"
    | "execute"
    | "escalate";

  budget?: WorkBudget;
  stopConditions?: Predicate[];
  recheckWhen?: Predicate[];

  confidence: number;
}

interface WorkOutcome {
  actualBurn: BurnVector;
  observedReturn: Partial<ReturnVector>;

  retries: number;
  reworkIntroduced: number;
  downstreamReuse?: number;

  forecastError: ForecastError;
}
```

Over time Projector learns predictors conditioned on things like:

```text
action class
semantic region
risk level
model / worker type
repository maturity
change size
uncertainty
dependency fanout
historical failure mode
```

But **policy self-modification should be evidence-gated**. Don't let three lucky tasks convince Projector that tests are obsolete.

Candidate policy adaptations should first run against historical/replay fixtures and whatever eval corpus Projector maintains before promotion.

That fits very nicely with the broader Projector idea of expensive cognition eventually crystallizing into cheaper persistent machinery.

# The sneaky-important invariant: economics applies to economics

I'd absolutely include this:

> **The cost of Work Economics analysis MUST itself be proportional to the plausible consequences of the candidate work.**

So Projector gets an economic materiality ladder.

A one-line typo does **not** get a Monte Carlo forecast, three agents, and a tribunal.

A cross-cutting architectural migration might.

That naturally yields something resembling the existing `quick / standard / deep` process-depth idea, which was already conceived as **risk-derived rather than ritual-derived**. fileciteturn2file2 But instead of those being merely presets, they become **initial policy bands selected by the economics engine**, with continuous escalation or contraction when evidence warrants it.

# One further upgrade: treat the whole development backlog as a portfolio

This is the rung above per-change efficiency.

Suppose Projector has five possible pieces of work:

| Work | Immediate value | Cost | Strategic consequence |
|---|---:|---:|---|
| Feature A | high | medium | none |
| Refactor B | low | medium | halves cost of A/C/D |
| Fix C | medium | tiny | unblocks testing |
| Research D | unknown | tiny | may invalidate A |
| Cleanup E | low | high | cosmetic |

A task-local optimizer starts A.

A **portfolio optimizer** may correctly do:

```text
C → D → maybe B → A
```

because the sequence changes the economics of everything downstream.

So Projector's objective should really be:

> **Choose not only which work is worthwhile, but the sequence of interventions that maximizes expected verified progress across the active horizon.**

That naturally intersects the implementation DAG, critical path, optionality, architecture decisions, and Change Cases.

It turns scheduling itself into reasoning.

## The one-line Projector doctrine I'd preserve

> **Spend intelligence only where its expected marginal effect on the outcome justifies the burn; spend the cheapest intelligence capable of resolving the current uncertainty; stop when additional work no longer materially changes the expected result; and continuously learn where those boundaries actually are.**

That feels like the proper formal spine for what you're after.

And I think it's more foundational than merely “quota optimization.” **It's an economics of cognition and intervention for software development.** Once Projector has this, Borg assimilation, model routing, research, testing depth, review, planning, parallelization, refactoring, and even its own future architectural evolution can all be governed by the same coherent principle.
