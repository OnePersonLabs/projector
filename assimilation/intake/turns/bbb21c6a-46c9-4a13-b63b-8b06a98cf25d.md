## Assistant

Your three requirements are directionally aligned with the clean spec, but **#3 reveals a real missing subsystem**. The substrate is there; the behavior you want is not yet guaranteed.

I’d frame the stronger idea not merely as *progressive disclosure*, but as **progressive architecture commitment**:

> **Do not make architectural decisions before their concerns become material. When requirements evolve, discover newly material concerns, invalidate decisions whose assumptions changed, research the current option space, and resolve only the decisions necessary to safely proceed.**

That is more powerful than a UI disclosure pattern.

### 1. The “why” is already almost exactly there

The clean spec's `AuthorityRecord` is essentially an evidence-backed ADR:

- conclusion;
- rationale;
- alternatives;
- assumptions;
- typed `reconsiderWhen`;
- evidence;
- authority vector;
- risk;
- who decided it.

And the `Rule` has its own rationale, while a Projection Lens points at the authority record that justifies it. fileciteturn5file0

So something like:

> use pnpm workspace catalogs to centralize dependency versions

should not merely exist as a line in config. Conceptually, Projector already has the machinery for:

```text
decision
  WHY:
    shared packages make version divergence costly
    workspace uses pnpm
    current pnpm capabilities support this cleanly
    alternative X adds no compensating value

  CONSEQUENCES:
    dependencies governed by catalog policy
    package manifests must not independently pin governed deps
    validator checks divergence
    migration transform normalizes existing manifests

  RECONSIDER IF:
    package manager changes
    repo stops being a shared-version monorepo
    pnpm mechanism materially changes
```

That fits Projector extremely well.

The hole is that the spec doesn't quite say **every material technical decision must have this relationship**. A Projection Lens does, but a technology selection can exist as an ordinary `decision` Concept without a normative guarantee that it has an Authority Record and explicit consequences.

I'd strengthen that eventually.

---

### 2. “Decision explains the rules it created” is weaker than I think you want

The spec currently has both halves:

```text
Authority/decision: why architecture should work this way
Rule/lens: how architecture must work
```

But it doesn't make their relationship explicit enough.

What you're describing is more like:

```text
Concern
    ↓
Decision
    ├── why
    ├── alternatives considered
    ├── assumptions
    ├── preferences involved
    ├── reconsideration conditions
    │
    └── consequences
         ├── rules
         ├── lenses
         ├── validators
         ├── transforms
         └── other decisions constrained
```

That gives you a very valuable bidirectional query:

```text
Why does this rule exist?
→ because decision D-17 chose centralized workspace dependency policy

What would changing D-17 affect?
→ these 4 rules, 2 lenses, 61 package manifestations,
  and decisions D-22 and D-31
```

The spec supports much of that indirectly through semantic relationships and impact rules, but **does not currently require the explicit decision→consequence relationship**.

I think that should become normative.

---

## 3. The larger missing idea: architectural concerns themselves need a lifecycle

This is where your cross-platform example exposes the gap.

Suppose the repository begins:

```text
simple React web app
```

There is absolutely no reason on day one to interrogate the developer about:

- monorepo orchestration;
- workspace dependency coherence;
- mobile packaging;
- desktop runtime;
- platform abstraction;
- API client generation;
- shared domain packages;
- cross-platform persistence;
- app-store release structure.

That would violate Projector's own anti-ceremony principle.

Then the developer says:

> make this web + desktop + iOS + Android.

The current Semantic Change Compiler can recognize an architecture-boundary/platform change, calculate impact, and potentially invoke modernization research. fileciteturn5file0

But the spec does **not require the following causal step**:

```text
new requirement
↓
discover newly material architectural concerns
↓
identify unresolved decisions
+
identify existing decisions whose assumptions are now false
↓
research only those dirty/new decision surfaces
↓
evaluate current alternatives
↓
present highest-leverage decisions
↓
accept decisions
↓
derive rules/lenses
↓
then plan implementation
```

That is the missing machinery.

### Your “dirty” intuition is exactly right

Projector already has excellent invalidation semantics for implementation projections. fileciteturn7file5

I think the same basic principle belongs **one semantic layer higher**:

```text
projection validity
    dependency changed → projection becomes suspect

architecture decision validity
    assumption/concern/constraint changed → decision becomes suspect
```

Not necessarily “wrong.”

Just:

> The proof that this was the correct architecture choice has expired.

That's beautifully consistent with the rest of Projector.

## Example: simple web app → cross-platform monorepo

I would expect Projector eventually to reason approximately like this:

```text
Requested capability change:
    targets += desktop, Android, iOS

New concerns activated:
    workspace/package architecture
    shared dependency consistency
    task orchestration
    cross-platform code sharing boundary
    UI/runtime strategy
    native capability boundary
    API contract strategy
    persistence strategy
    build/release topology
    platform-specific testing
    distribution/signing
```

But crucially, **not every concern needs an immediate decision**.

For example:

```text
BLOCKING NOW
  application/runtime architecture
  monorepo/workspace shape
  shared-code boundary

MATERIAL SOON
  dependency-version policy
  task graph/cache strategy
  API contract mechanism

DEFER
  release automation
  store metadata automation
  sophisticated remote caching
```

That is the actual progressive-disclosure behavior I think you're after.

It's **just-in-time architecture** without becoming **just-wing-it architecture**.

## Nx/Turbo is a good example of why the system shouldn't encode canned answers

The rule shouldn't be:

> monorepo → use Turbo.

Nor:

> monorepo → evaluate Turbo and Nx every time.

Instead the new state activates a concern such as:

```text
concern: workspace-task-orchestration
```

Projector then asks whether the repository actually has the forces that make an orchestration layer valuable:

```text
multiple independently buildable packages?
dependency-aware task ordering?
expensive repeated builds?
CI caching opportunity?
affected-only execution?
large enough graph to justify tooling cost?
```

Perhaps the answer is:

> pnpm scripts are sufficient; no orchestrator yet.

That itself becomes a decision whose reconsideration trigger might be:

```text
package count > threshold
OR CI duration exceeds threshold
OR dependency-aware task scheduling becomes necessary
OR remote cache becomes valuable
```

Then **Turbo/Nx never even gets pushed on the developer until the concern has sufficient leverage**.

That is exactly the kind of architecture intelligence I'd want Projector to develop.

# The preference part is genuinely absent

The current spec contains `prefer` rules and gives approved user intent high authority, but there is no proper **developer preference model**. fileciteturn7file18

I think there should eventually be three distinct layers:

```text
Developer / organization preferences
        ↓ soft priors
Project-specific preferences
        ↓ stronger contextual priors
Accepted project decisions
        ↓ authoritative architecture
```

That distinction matters.

Suppose your general preference is:

```text
prefer TypeScript
prefer managed infrastructure
prefer minimal operational burden
prefer boring/stable technology
```

For Project A you may nevertheless decide:

```text
Rust is justified for this realtime native component.
```

The system should not treat that as inconsistency.

Conversely, if evaluating:

```text
Tauri vs Electron vs React Native vs Flutter vs native shells
```

your accumulated preferences should dramatically reduce pointless questioning and alter option rankings.

Something like:

```text
general preference:
  TypeScript ecosystem             strong
  minimize bespoke native code     medium
  maximize shared code             strong
  minimize cloud ops               strong

project constraint:
  browser target required          hard
  MIDI latency < X                 hard
  native USB access                hard

research:
  current platform capabilities
  active maintenance
  official support
  packaging restrictions
  performance characteristics

→ ranked architecture proposals
```

The preferences inform the search.

They **do not override hard reality**.

## And I would not store personal preference exactly like repo architecture

This is an important boundary.

A developer's reusable preference:

> Prefer TypeScript where there is no compelling reason otherwise.

probably should **not automatically become committed repository governance**.

I would conceptualize:

```text
user-level profile
~/.projector/preferences
        ↓
decision-support input

project-level adopted preference
.projector/...
        ↓
canonical soft rule

accepted project decision
.projector/decisions/...
        ↓
normative authority
```

That way a shared repository doesn't accidentally canonize Michael's personal tastes merely because Michael initialized Projector.

The project can *adopt* one.

# Live research: mostly present, but I'd broaden the trigger

The current spec's Research Boundary is good. It requires external research when a pattern may become normative, alternatives materially differ, modernization is proposed, platform constraints are uncertain, security/support matters, or local evidence conflicts. It prioritizes official docs/specifications and records freshness/applicability. fileciteturn5file0

That covers much of your requirement.

The extension I'd make is:

> **A newly activated or dirty architecture decision whose outcome materially depends on a changing external ecosystem should require fresh-enough research before being resolved.**

So if:

```text
decision:
    cross-platform runtime
last evaluated:
    18 months ago

trigger:
    new iOS target introduced
```

then the old decision isn't merely re-read.

Its supporting evidence becomes stale relative to the changed question, and Projector reopens the relevant option space.

This fits naturally with the existing typed `AuthorityReconsiderTrigger` system. fileciteturn5file0

# The architecture I'd add conceptually

I wouldn't bolt this onto the modernization engine.

It's broader than modernization.

I'd think of it as a first-class **Architecture Decision Lifecycle**:

```text
Requirement / constraint delta
        ↓
Concern activation
        ↓
Decision impact analysis
        ├─ new unresolved decisions
        └─ existing decisions made dirty
        ↓
fresh evidence / research where required
        ↓
preference-conditioned option evaluation
        ↓
progressively disclose material decisions
        ↓
decision acceptance
        ↓
rules + lenses + impact rules
        ↓
implementation planning
```

And this should happen during an ordinary feature request, not only when somebody explicitly runs:

```text
projector upgrade
```

That distinction is the main thing I think your three points add to the clean spec.

### Bottom line

**#1 is ~90% already represented.  
#2 is ~75–80% represented.  
#3 is perhaps ~50% represented structurally, but the missing 50% is high-leverage.**

The existing architecture is unusually well-positioned for it because the hard parts already exist: semantic changes, typed impact, authority records, reconsideration triggers, research, rules/lenses, information-gain interaction, and state-bound planning. fileciteturn5file0

What is absent is the explicit middle layer:

> **“What architectural concerns has this new intent made relevant, and which prior architectural conclusions no longer have a valid basis?”**

I think that deserves to become a central Projector capability rather than being treated as an embellishment to `upgrade`.
