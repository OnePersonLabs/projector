# Don't route every turn. Route cognition.

Instead of:

```text
Michael decides:
Sol High
Sol XHigh
GPT-6 High
GPT-6 XHigh
Sol High
...
```

make the system:

```text
┌──────────────────────────────────────┐
│       IMPLEMENTATION AGENT           │
│       GPT-5.6 Sol High               │
│                                      │
│ owns task, edits code, tests, loops  │
└──────────────┬───────────────────────┘
               │
       detects uncertainty/risk
               │
               ▼
┌──────────────────────────────────────┐
│       REASONING CONSULTANT           │
│       GPT-6 High                     │
│                                      │
│ diagnose / architect / challenge     │
└──────────────┬───────────────────────┘
               │
       genuinely gnarly?
               ▼
┌──────────────────────────────────────┐
│       DEEP CONSULTANT                │
│       GPT-6 XHigh                    │
│                                      │
│ resolve deep ambiguity / invariants  │
└──────────────────────────────────────┘
```

Then control returns to **Sol High** for implementation.

That means *you* don't drive the stick shift. The Sol agent does.

And crucially, **GPT-6 doesn't need to implement the whole thing**. It might consume 20k tokens understanding the hard part, return a compact decision/invariant/diagnosis, and then disappear.

That's much more quota-efficient than letting GPT-6 spend its premium brainpower watching `pnpm test` scroll by.

# What should trigger escalation?

I would make it **mostly deterministic**, not "use GPT-6 whenever you feel confused."

The Sol runner gets instructions roughly equivalent to:

### Stay on Sol High normally.

Escalate to **GPT-6 High** when any of these happen:

- the task requires choosing or changing an **architectural boundary**
- multiple plausible implementations have materially different consequences
- the change affects a **core invariant**
- behavior contradicts the current model of the system
- implementation requires understanding interactions across several subsystems
- the first serious implementation attempt fails for a reason that isn't immediately local
- a requested change conflicts with an existing spec/rule/eval
- the agent is about to introduce a new abstraction because existing ones don't fit
- fixing something seems to require exceptions/special cases
- the agent cannot succinctly state **why the proposed fix is correct**

Escalate from GPT-6 High to **GPT-6 XHigh** only when:

- GPT-6 High still has competing hypotheses
- correctness has unusually large architectural blast radius
- the issue appears to expose a flaw in the system's fundamental model
- repeated attempts have failed
- you're establishing an invariant that lots of future work will depend on

Then return the answer to Sol.

That eliminates probably **90% of the model-selection burden**.

## And I would mostly delete Sol XHigh from the router

This conversation has changed my view of its usefulness.

For your quota optimization, I'd make the hierarchy:

```text
Sol High
   │
   ├── ordinary complexity ──────────────► keep going
   │
   └── epistemic uncertainty
              │
              ▼
          GPT-6 High
              │
              └── exceptional unresolved depth
                         │
                         ▼
                     GPT-6 XHigh
```

**Sol XHigh becomes an optional specialized mode**, not a normal escalation step.

Its niche is:

> "We know exactly what we're doing, but executing it correctly requires a ton of careful simultaneous reasoning."

That's real, but less common than the cases where what you really need is **better cognition rather than more cognition**.

OpenAI even recommends trying Astra Low/Medium when users were previously happy with Sol High, specifically noting that lower reasoning on Astra can outperform higher reasoning on Sol. citeturn234222search0

# Codex can actually support this architecture

Current Codex has configuration for:

```toml
model_reasoning_effort
plan_mode_reasoning_effort

[agents]
default_subagent_model
default_subagent_reasoning_effort
```

and the current implementation of `spawn_agent` supports a model and reasoning-effort override for children. citeturn822237search1turn682319search3turn682319search10

So conceptually a Sol parent can do:

```text
"This crossed an escalation condition."

spawn:
    GPT-6
    high
    focused problem statement
    minimal relevant context
```

and continue afterward.

### There is one wrinkle.

Codex's multi-agent/model-override machinery has had **recent bugs and UX inconsistencies**, especially around Desktop, Windows, named roles, full-history forks, and model override inheritance. There are current issue reports around exactly this area. citeturn682319search2turn708157search0

So I would **test the routing mechanism once in your actual Projector environment** rather than assuming a pretty TOML file means the child really got GPT-6.

The current codebase supports the concept. The plumbing has been moving quickly.

# There's an even better Projector-ish version

Don't route purely from fuzzy words such as "architecture."

Have the runner calculate a tiny **escalation score** from observable conditions:

| Signal | Add |
|---|---:|
| Changes architectural boundary/invariant | +3 |
| Novel/unfamiliar subsystem | +2 |
| Crosses 3+ packages/subsystems | +2 |
| Two genuinely plausible approaches | +2 |
| Prior implementation attempt failed | +2 |
| Spec/eval/code disagree | +3 |
| Requires exception to existing pattern | +2 |
| Purely mechanical/spec-prescribed | −3 |
| Existing pattern clearly applies | −2 |

Then:

```text
score <= 2
    Sol High handles it

score 3-6
    Sol High asks GPT-6 High for a bounded consultation

score >= 7
    GPT-6 High gets a deeper investigation

GPT-6 High explicitly reports unresolved high-risk uncertainty
    GPT-6 XHigh
```

I wouldn't obsess over those exact weights. The important conceptual upgrade is:

> **Escalation is based on epistemic risk, not apparent task size.**

A 900-line implementation can be Sol High.

A six-line change to a foundational invariant can deserve GPT-6 XHigh.

That's the distinction agents usually screw up.

# And quota itself can become an input

Eventually I'd make the router **quota-aware** too.

Same task, different policy depending on available allowance:

```text
NORMAL
Sol High → GPT-6 High → GPT-6 XHigh

CONSERVE
Sol High → GPT-6 High only on hard triggers
         → XHigh only after an actual failure

ABUNDANT / near reset
Sol High → proactively consult GPT-6 on architectural decisions
```

So you're optimizing something closer to:

\[
E[\text{total quota to verified completion}]
\]

rather than:

\[
\text{quota this turn}
\]

Now we're basically doing **compute allocation as an engineering resource**, which feels extremely on-brand for Projector.
