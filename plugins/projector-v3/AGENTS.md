# Projector

When the target repository has `.projector/config.toml`, use `$projector` to retrieve relevant accepted meaning before choosing behavioral or architectural edits. Read the obligations, rationale and open questions, then work with normal Codex tools within the user's authorization. Check affected meaning and behavior afterward. Installation alone does not activate a repository.

The model owns accepted intent. Code, plans, retrieved candidates and assimilation notes are evidence to assess against that intent. Use `$projector-change` when intended meaning changes; retain existing identities and explain the change. An authorized implementation that preserves accepted meaning does not need a second execution through Projector.

Resume with the actual retained context, change or approval ID. Rehydrate and check currentness before reusing a conclusion. Resume only inspects; application and recovery are explicit. Preserve ambiguous or unfinished evidence. If Projector is unavailable, read the canonical Markdown directly and state the missing assurance.

Use `$projector-review` for project-aware review of an actual change. Follow typed relationships through producers, consumers, persistence, registrations and tests; give concrete counterexamples and distinguish violations from unknown evidence. Reuse Codex execution and delegation. Projector does not own a second task queue.
