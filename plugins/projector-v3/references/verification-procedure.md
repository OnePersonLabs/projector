# Verification procedure

This reference holds the shared verification procedure. Keep change-specific obligations and results in the task's normal evidence notes. Do not copy this procedure into each plan.

## Select the context

For ordinary repository work, use the actual checkout, selected baseline, repository commands, and existing review gates. This procedure does not activate Projector or require managed publication.

Apply test maintenance and implementation repairs only within existing authorization. For a review-only request, report proposed changes instead of editing source or tests.

For a repository with `.projector/config.toml`, use the relevant accepted meaning already retrieved through [$projector](../skills/projector/SKILL.md). Retrieve focused current context if the relevant meaning is missing or stale. Retain the actual context ID. After behavior checks, run `projector check <context ID>` through the CLI defined there and review the actual result through [$projector-verify](../skills/projector-verify/SKILL.md). These commands do not replace executable checks or authorize publication. Do not restart the whole main workflow merely to select verification.

For planning, derive obligations and the test-change plan. Validate artifacts with the actual repository validator. Report checks that require implementation as unexecuted. Do not invent a prepared checkout, change ID, or evidence API.

For branch integration, retain the actual target baseline and integration checkout. Assess the complete target-to-integration difference, including corrections, generated files, and hook writes. Use ordinary Git, repository checks, and the applicable integration review gates. Reconcile actual changed inputs after merge, rebase, or squash. Target movement alone does not invalidate checks whose relevant inputs still match. Publication requires its own authorization.

## Establish obligations and protection

1. Read requirements, designs, repository instructions, required checks, and relevant producers and consumers. Map changed behavior, surviving invariants, boundaries, shared setup, and failure paths. For fresh behavioral work, write a compact inventory with discriminating examples before inspecting existing assertions. Use accepted requirements and boundary behavior as the oracle. Do not derive expected results from the edited implementation. For existing work, state the historical limitation; do not claim retrospective test-first evidence.
2. Inspect tests against that inventory. Keep valid protection. Create protection for uncovered obligations or material risks. Update changed expectations and state both old and new obligations. Refactor test structure while preserving assertions. Replace inadequate protection with equivalent or stronger protection. Delete tests only for retired obligations or protection demonstrably preserved elsewhere. Shared code coverage alone does not prove redundancy. Record applicable decisions and reasons; do not make six artificial changes. Keep this test-change plan separate from execution selection. Author tests per coherent slice. Deletion-only cleanup does not require an absence test. Add recurrence guards only when repository policy permits them and a concrete recurrence mechanism or protected invariant justifies them.
3. Select execution from the inventory, complete baseline difference, dependencies, and repository commands. An affected test can require execution without modification. Deduplicate overlapping checks only when their actual assertions cover the same obligations. Investigate unknown relationships. Widen empty, uncertain, or unreliable selections. Preserve required full checks, release checks, hooks, CI, and review gates.

## Verify at coherent checkpoints

Do not automatically run tests after every edit. Revisit impact when new callers, fixtures, setup, configuration, dependencies, dynamic boundaries, or obligations appear.

1. **Before each slice:** Establish a relevant pre-edit baseline where practical. Reuse matching evidence and report limitations. Keep pre-existing failures separate from introduced failures. For changed behavior, specify an independent oracle and expected failure; observe the discriminating check fail for the intended cause before implementation. Infrastructure failure is not the intended red. Pure refactors, already-correct behavior, and nonbehavioral work can use existing protection or applicable validation without a new red. Explain the exception. For historical work, state that no pre-edit red was observed; do not reverse accepted work to manufacture one.
2. **After each slice:** Run checks that discriminate the changed behavior and affected integration. Inspect output, exit status, and actual cases. Fix causal failures and revise impact when dependencies appear. A build, mock, or dispatch-only check establishes only the behavior it exercises. A small change can combine this checkpoint with final verification.
3. **After test maintenance:** Confirm protection for every surviving obligation. For infrastructure cleanup, establish that original checks retain their protection before changing expectations. Check fixtures, setup, infrastructure, and selection before changing expectations in response to failure. Establish replacement protection before removing old protection. Remove obsolete assertions for intentionally retired behavior and identify the retired obligation. Run maintained checks and reject passing empty selections. Do not weaken expectations to fit an implementation failure.
4. **Final settled result:** Recompute impact from the complete selected-baseline difference, including committed, staged, unstaged, and untracked task work. Include hook and generated writes. Reconcile obligations, protection decisions, and execution selection. Deduplicate covered checks and widen uncertain coverage. Run every required full and release check. Reuse evidence only when implementation, inputs, configuration, environment, services, and actual coverage still match. A new session or another branch merging alone is not a reason to repeat unaffected checks. A pass from another checkout does not establish protection for changed inputs in this checkout.

Batch expensive broader checks at the applicable handoff, PR, integration, or release checkpoint. Run them earlier when a concrete failure, impact, or risk requires it, and state the reason. Preserve repository hooks. Do not choose push as a checkpoint or install a hook merely by applying this skill.

## Record evidence and review

Keep compact notes of commands, actual results, covered obligations, failures, and evidence locations. Retain failed results. A later pass does not erase an unresolved obligation. Baseline observations and intended failures are history, not final assurance. Historical passes are not current passes. Source, tests, configuration, and authority changes invalidate the corresponding assurance; task bookkeeping alone does not necessarily invalidate application checks. Check actual input relationships before reuse.

Follow applicable repository review gates. Use independent review for consequential authority, persistence, or architectural changes and when it adds a distinct perspective. Give the reviewer the actual target, complete baseline difference, protection decisions, executed results, and remaining limits. Ask for missing consumers, counterexamples, unsupported structure, incomplete migration, and the strongest simpler alternative. Resolve findings and obtain required review of material corrections. Refresh checks whose inputs changed. Do not invent review attribution or require an agent for every slice.

Report protection decisions, commands and cases executed, baseline and intended-red results or justified exceptions, final coverage, reused evidence, and actual review attribution. Identify unresolved failures, unexecuted checks, and uncertainty. Do not report inferred runtime or native behavior as observed behavior. Completion requires the applicable checks and review to support the settled result.
