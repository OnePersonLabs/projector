# Strict change proposal

This guide and [change-proposal.schema.json](change-proposal.schema.json) are generated from the strict `ChangeProposalSchema` exported by `@projector/core`. Do not edit either generated file by hand.

Write one JSON document that validates against the generated schema. Unknown top-level or nested fields fail closed. Repository paths must be canonical, repository-relative, non-reserved paths. Exact edits cannot overlap independent validators. Requirement, scenario, alias, validator, and architecture-deferral constraints are enforced by the same core parser used by the installed lifecycle.

Submit the proposal in the `proposal` field of a versioned `change.capture` request through the [bundled operation runner](../../references/operation-contract.md), with the intended repository, request and retained context ID. A proposal is interpretation evidence, not approval or mutation authority.

Existing requirement and scenario identities preserve their canonical payload without a rewrite when their title and meaning are unchanged. To revise existing meaning, supply `revision` with its stable `id`, current `expectedSemanticHash`, and a concrete `rationale`. Missing, mismatched, stale, and no-op revisions fail. Identity aliases locate existing meaning; they do not authorize renaming it. The plan's `preview.intentReview` shows preserved, added, and revised commitments plus related canonical obligations, including targets without current code. These checks do not prove that tests cover every commitment or that an implementation preserves the whole design.

For a model-only transaction, omit `edits` and `validation`. Requirements and scenarios may also be omitted when `canonicalMutations` establishes typed records. The full `requirement` and `behavioral-scenario` variants can preserve a future capability before code exists or revise its explicit scope, provenance, status, and complete meaning. Use these variants when the shorthand's inferred scope is insufficient; a mapping is not proof of fulfillment. Other kinds include concepts, relationships, concerns, project preferences, decisions, lenses, and authority records. Set `architecture: null` unless proposing a bounded architecture deferral; architecture decisions themselves belong in `canonicalMutations`. Always include `analysisFacets: ["behavior", "architecture"]`.

An `architecture-concern` is an authored, scoped question with materiality, related meaning, decision references, and an explicit disposition. A resolved concern needs an active decision. A deferred concern preserves options, forbids premature commitments, and states reconsideration conditions. A `developer-preference` stored in a repository must be explicitly adopted with `scope: "project"`. New decisions bind the current preference hash; later soft-preference changes do not rewrite their historical influence. A declared non-advisory decision consequence requires its actual canonical target product in the final transaction state, matching its declared scope and payload fields. The compiler cannot invent a missing lens, constraint, or migration from prose.

Changed decisions must remain indexed by their owning concern. Retiring or superseding its sole active answer also requires an explicit concern disposition. This bounded authoring route requires normalized decision and concern scopes to match; use an explicitly scoped concern for another boundary. Touched decision-constraint cycles are rejected because no convergence-proof input is supported. Authenticated user/organization preference providers and typed technology products are unavailable: explicitly adopt project preferences, and record technology choices/options in the decision and concrete constraint concepts. The `select-technology` and `deprecate-technology` consequence variants are rejected rather than treating an arbitrary concept as a technology catalog entry.

Typed canonical record additions and revisions have `kind`, `operation`, `rationale`, and the `payload` shown in the schema. An addition requires `expectedAbsent: true`. A revision requires the current envelope's `expectedSemanticHash` and `expectedDocumentHash` (the `canonicalDocumentHash` field), preserves the record's ID, and includes the complete replacement payload. Do not supply derived semantic or discovery hashes. The compiler derives lens-rule hashes too. Read current accepted envelopes when revising; never invent their hashes. The plan retains before/after meaning and rationale.

An empty canonical repository may bootstrap new authored meaning without an identity context. When accepted durable meaning already exists, adding or separating meaning requires an inspected context and an `identityResolution` whose `contextId` and `contextHash` match it. Outcomes that create, split, or replace an identity require an explicit `newBoundary` describing what the new identity owns and excludes. Candidate similarity is not identity authority.

Identity retirement uses the payload-free `canonicalMutations` variant with `kind: "lineage"` and `operation: "add"`. Supply `lineageKind`, exact source IDs/kinds/current semantic and document hashes, intended `replacementIds`, and rationale. Split, merge, move, replacement, and deletion cardinalities are enforced. The compiler derives immutable lineage and tombstone records, binds them to the observed canonical state, and removes the retired source in the same journaled transaction. Active references to a retired identity must be revised or retired in that transaction; hashes and replacements must never be invented.

For example, this establishes a named future capability without pretending its implementation exists:

```json
{"apiVersion":"projector.change-proposal/v1","architecture":null,"analysisFacets":["behavior","architecture"],"canonicalMutations":[{"kind":"concept","operation":"add","expectedAbsent":true,"rationale":"Preserve the user's authorized future capability before implementing it.","payload":{"id":"concept:future-export","key":"future-export","kind":"capability","name":"Future export","aliases":[],"statement":"A future export retains source provenance. Its encoding remains undecided.","status":"active","sourceClass":"authored","confidence":1,"tags":["future"],"evidence":[]}}]}
```

Model-only approval authenticates the proposed model transaction. Its validation covers canonical integrity, references, and eligible lens compilation; it does not establish runtime fidelity. Code-bearing proposals retain the independent-test and controlled-execution requirements. When the host implements code under its own authorization, reconcile the saved context and inspect structural results and independently checked behavior separately.
