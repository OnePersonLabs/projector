# Installed Projector control loop

Use this guide to choose and resume the supported installed workflow. The [operation contract](operation-contract.md) owns the exact request envelope and documented inputs; `packages/core/src/schemas/operations.ts` and the packaged handlers own the executable schema. This map is a review aid, not a source of new authority, a progress store, or proof that a scenario passed. Read only the rows relevant to the current work. Every request names the absolute target repository. The runner reports readiness and operation access; `status` is useful when either is unclear, not a mandatory preflight before every call. An inactive repository needs user-authorized `init` before ordinary operations.

## Responsibility and continuation

The invoking agent owns the control loop across process and session boundaries. Retain the saved context ID, proposal file, change and approval selectors, reviewed immutable plan hash, result, receipt, and recovery record in their existing owners. An operation result proves delivery to a process boundary, not that an agent acted on it. On a new session with retained anchors, start with `cleanup` using those anchors and inspect its continuation before choosing the next operation. Before reusing reasoning after host edits, `reconcile` the saved context and refresh affected reasoning when dependencies changed. Distinguish its binding status from governance predicates and application-evidence currentness. Stale knowledge is a refresh or replan question; an observed violated predicate is a design finding.

On interruption or an uncertain return, inspect the last durable result and `cleanup` with the retained selector or context ID. Follow its bounded `continuation.drillDown`, paging with the returned evidence identity; restart the page at offset zero if evidence changes. Inspect current, stale, and unknown binding, governance, historical lifecycle status, missing artifacts, and `continuation.nextAction` before choosing an operation. The next action is an invocable request, not approval or completion. Recovery of an unfinished effect has priority over a new capture or apply. `operation-access.recover` handles only recognized expired access claims from exited processes; `change.recover` and `change.resume` handle an authenticated interrupted approved lifecycle. A changed proposal, stale approval, changed representation profile, or unresolved semantic dependency needs a new plan and exact approval. Do not use access recovery as lifecycle recovery, or lifecycle recovery as permission to replan. Never rerun committed effects merely to republish a missing result.

An ordinary authorized host edit may realize accepted meaning. It needs relevant behavioral checks and post-edit context reconciliation; it does not acquire Projector's controlled-execution certificate. For a canonical revision or controlled execution, use capture, plan, inspect, exact-hash approval, apply, then authenticated result and journal inspection. Preserve still-applicable obligations when replanning. `coverage`, `complete`, `cleanup`, and `verify` provide bounded observation and questions; none accepts meaning or grants execution authority.

The source of each registered capability remains its accepted canonical obligation, rather than its registration alone. `status`, `init`, and `operation-access.recover` implement the installed runner decision (`decision:bundled-operation-runner`) and durable project ownership (`requirement:durable-meaning`). `repository.check` implements `requirement:reverse-reconciliation`. `context` and `reconcile` implement `requirement:pre-edit-relevance` and `requirement:scoped-invalidation`. `change.capture`, `change.plan`, `change.approve`, `change.apply`, `change.recover`, and `change.resume` implement `requirement:durable-meaning` and `requirement:coordinated-worktree-writes`; `representation.inspect` and `representation.reconcile` additionally serve `requirement:executable-lenses`. `coverage`, `complete`, and `cleanup` serve `requirement:evidence-bound-completion`. `verify` serves `requirement:executable-lenses`. The conditional `application.observe` serves `requirement:runtime-evidence-legibility` and `scenario:inspect-isolated-application-behavior`. These links identify intent to assess, not independent proof of each implementation.

## Application review boundary

For `application.observe`, match the plan repository root and owned artifact root to the target, and bind resolved toolchain files to exact plan pins. Inspect the returned outcome, operation status, input currentness, build and served bytes, browser assertions, host assumptions, diagnostics, and every owned resource's cleanup result. A published artifact is evidence to interpret, not an automatic pass. A passed browser case supports only its named observations. Failed assertions retain diagnostics; unavailable collection is unknown; incomplete cleanup is a recovery problem even if an assertion passed. Recheck freshness before using a past run for a changed revision. Route the evidence through `$projector-review` alongside the relevant scenario and independent checks.
