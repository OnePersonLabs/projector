---
name: openspec-x-projector
description: Complete a Projector change using nested OpenSpec requirements and design deltas, an isolated candidate, current executed evidence, and coherent archive.
---

Use the installed Projector MCP tools or equivalent `projector <operation> --json '<object>'` commands. Keep `root` and `change` fixed after selecting the repository and active change. The companion OpenSpec workflow plugin is not a runtime dependency.

1. Read the affected live requirements, concern contracts, current change artifacts, and relevant implementation. Express intended behavior in nested OpenSpec requirement deltas and decisions in separate nested design deltas. Keep specifications under `specs/**/spec.md`, designs under `designs/**/design.md`, and one editable task tree in `tasks.md`. Use only bracket references such as `[[spec:audio/preview#Immediate replay]]`.
2. Call `prepareChange` with `{root,change}`. It pins the accepted baseline, projects requirements with the pinned OpenSpec CLI, applies exact design deltas, records a durable target, and allocates a separate candidate worktree. Keep the returned candidate identity. Open it with the managed observation profile before implementation, and use acknowledged begin/end mutation batches for its participating writes. Unknown shell writes require a checkpoint before claiming working-current results.
3. Call `validatePlan`. Supply applicability dispositions with a requirement reference, executable selector objects, and an inclusion or scoped exclusion reason. Supply contributions with a path, current decision reference, exact `target` for symbol-level realization, action `retain`, `remove`, `replace`, or `revise`, and current reason. An example selector is `{kind:"path",root:".",prefix:"src/audio"}`. Treat unknown or empty populations as obligations. Read the returned independent changed-artifact inventory and previous contribution set.
4. Call `applyChange` and implement in the candidate. A task edit is input: preserve it, determine whether it changes scheduling or proposes behavior, and amend the actual requirement/design authority for behavior changes. Revalidate the plan. For changed task wording, provide a `taskChange` disposition with `kind`, `reason`, and current `targetId`; this classification never disables product gates.
5. If intended meaning changes during partial implementation, revise the source change artifacts and call `reviseChange`. Review its scoped target diff. Keep justified contributions, including valid contributions in a file with obsolete code. Remove obsolete routes, exports, registrations, flags, dependencies, tests, and abstraction layers in the affected closure. Do not restore whole files merely because a target changed.
6. Call `recordEvidence` with an executable `command`, argument array, exact path `scope`, and bounded `timeoutMs`. This runs the check in the candidate and records its real outcome and input basis. Use checks that discriminate the changed behavior and removed architecture. A successful no-op command is not useful behavioral evidence. Failed, stale, or mutation-producing checks cannot authorize completion.
7. Obtain one real isolated reviewer for material choices. Provide the current target, previous contribution dispositions, actual diff, and executed evidence. Ask the reviewer to find a missing concern, unsupported retained structure, and a counterexample, and compare the credible simpler alternative. Record the review through `validatePlan` with `{basis,reviewer,examined,alternative,findings}`. The reviewer field is attribution, not a cryptographic proof of independence. Never invent a reviewer or report a simulated review as independent evidence.
8. Resolve every reported completion obligation. Call `finishChange` once. It verifies evidence and applicability, applies the exact target, uses supported OpenSpec merge/validation/archive, and updates only the allocated candidate branch with an expected-old-ref check. Do not invoke a second generic finish pipeline. A moved baseline or branch requires a scoped refresh. Main integration, deployment, and publication require their own authorization.
9. If interrupted, call `resumeChange`. It reconstructs from durable state and Git targets, recognizes an exact archive/publication, and performs only remaining bookkeeping. Unmet prerequisites keep the candidate blocked. Run finish a second time after settling to verify a substantive no-op.

Escalate unresolved consequential interpretation with observed evidence, alternatives and consequences, a recommendation, and the opportunity to give another answer. Ordinary supported implementation choices can proceed without a separate approval ceremony. Report installed version, observation profile, commands/results, operation costs, actual review provenance, and any unverified behavior accurately.
