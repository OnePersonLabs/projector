---
name: verify
description: Plan impact-aware checks, preserve test protection, execute evidence at coherent checkpoints, and independently review the final Projector change.
---

Read [the runtime contract](../apply/references/runtime.md). This skill owns the shared verification procedure. Tasks describe concrete work for the selected change; do not put this procedure into tasks.md.

1. Recover the selected implementation checkout. Read current requirements and designs, the complete baseline difference, repository checks, and relevant producers and consumers. Reconcile changed authority and substantive task wording first. For fresh behavioral work, derive obligations and discriminating examples before reading existing assertions. For already edited work, state the historical limitation; do not invent retrospective test-first evidence.
2. Make a test-change plan. For each affected test or obligation, decide whether to keep, add, update, refactor, replace, or delete protection, and explain why. Inspect assertion quality after deriving obligations. Preserve surviving protection; never weaken a test to fit the implementation. Deleted implementation can require deleting its tests without an absence guard. Add recurrence guards only when policy permits them and a concrete recurrence mechanism or protected invariant justifies them.
3. Choose execution separately. Use existing commands and dependency information to select checks that discriminate changed behavior and integration. Record the expected failure before a behavioral slice and confirm the intended cause. Explicitly identify pure refactors, already-correct behavior, and nonbehavioral changes when no new red is appropriate. Keep failed evidence as history.
4. Implement and check coherent slices. Do not automatically rerun tests after each patch. Revisit impact when new callers, shared fixtures, setup, configuration, dependencies, dynamic boundaries, or obligations appear. Broaden execution when selection is empty or unreliable. Unknown relationships are investigation obligations, never evidence of no impact.
5. At the settled checkpoint, recompute impact from the complete baseline difference, including committed, staged, unstaged, and untracked work. Run required repository and release checks. A matching broader check can satisfy narrower obligations. Reuse evidence only when implementation, inputs, configuration, environment, and services still match. A new session alone is not a reason to rerun checks.
6. Execute checks through `recordEvidence({root,change,command,args,scope,timeoutMs})`. Scope names exact files meaningfully covered. Inspect real exit status and output. Record provenance and platform limits: compilation, mocks, and dispatch-only tests do not prove runtime or native behavior. Failures require a causal fix or a precise remaining obligation.
7. Use verificationBasis for check freshness and the current plan/review basis for review. Checkbox changes and result bookkeeping do not automatically invalidate application checks. Substantive task changes need reconciliation. Changed source, tests, relevant configuration, or authority invalidate corresponding assurance; unknown coverage requires broader checks. Historical passes are not current passes.
8. Obtain a real independent final reviewer through a native subagent or separate reviewer environment. Supply the actual target, complete diff, contribution dispositions, test-change plan, executed results, and remaining limits. Ask for missing consumers, unsupported structure, invented justification, incomplete migration, counterexamples, and the strongest simpler alternative. Do not require another agent for every slice or invent attribution.
9. Call `validatePlan` with `review:{basis,reviewer,examined,alternative,findings}`. Resolve findings and obtain review of material corrections. Refresh checks whose inputs changed. Report actual checks, remaining unverified behavior, and attribution. Continue to $projector:finish when completion is authorized.

Completion: eligible executed evidence and attributed independent review support the settled implementation; otherwise precise obligations prevent completion.
