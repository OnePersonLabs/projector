This skill owns the shared verification procedure. Tasks describe concrete work for the selected change; do not copy this procedure into tasks.md. Read [the runtime contract](../apply/references/runtime.md) when using prepared-change operations.

## Select the verification context

- **Planning:** Derive obligations and a test-change plan while authoring artifacts. Validate complete artifacts with the bundled strict OpenSpec validator. Do not call `prepareChange` merely to plan checks or validate a draft. Report checks that require implementation as unexecuted.
- **Ordinary repository work:** Use the actual checkout, its selected baseline, normal repository commands, and ordinary evidence notes. Preserve repository checks, hooks, release requirements, and review gates. This procedure does not activate Projector or require a managed change.
- **Prepared Projector change:** Retain the actual source `root`, `change`, returned `candidateRoot`, and pinned baseline. Recover the selected candidate and state; do not substitute a newer checkout. Execute checks with `recordEvidence({root,change,command,args,scope,timeoutMs})`. Use `validatePlan` for current plan obligations and independent review. Continue to $projector:finish only when completion is authorized.
- **Branch integration:** Use the pinned `targetHead` and isolated integration checkout supplied by $projector:merge. Assess the complete target-to-integration difference, including corrections and hook writes. Use normal repository commands and evidence notes, and obtain mandatory independent review. Do not call `prepareChange`, invent a change ID, or use `recordEvidence` or `validatePlan` for this context. Publication remains owned by $projector:merge.

## Establish obligations and protection

1. Read current requirements, designs, repository instructions, required checks, and relevant producers and consumers. Map affected behavior, preserved invariants, input/output boundaries, shared setup, and failure paths. For fresh behavioral work, write a compact independent inventory with discriminating examples **before inspecting existing assertions**. Use approved requirements and boundary behavior as the oracle; the edited implementation must not define its own expected result. For work that already exists, state the historical limitation. Do not invent retrospective test-first evidence.
2. Inspect existing tests against that inventory. Make justified protection decisions from six categories. **Keep** valid surviving protection. **Create** missing protection. **Update** changed expectations, stating both old and new obligations. **Refactor** test structure while preserving assertions. **Replace** inadequate protection with specified equivalent or stronger protection. **Delete** tests only for retired requirements or when their protection is demonstrably preserved elsewhere. Shared code coverage alone does not establish redundant protection. Record the applicable decisions and reasons, not six artificial changes. Keep this test-change plan separate from execution selection. Author tests for each coherent slice; do not implement all planned tests speculatively up front. Never weaken expectations to fit the implementation. Deletion-only cleanup does not require an absence test. Add recurrence guards only when policy permits them and a concrete recurrence mechanism or protected invariant justifies them.
3. Select execution from the inventory, complete baseline difference, dependency information, and repository commands. Deduplicate overlapping checks. A broader check can satisfy narrower obligations only when its actual assertions cover them. Investigate unknown relationships; do not treat them as no impact. Widen empty, uncertain, or unreliable selections. Keep required full checks, release checks, hooks, and review gates even when focused checks pass.

## Check at four coherent checkpoints

Do not automatically run tests after every edit. Use these checkpoints and revisit impact when new callers, fixtures, setup, configuration, dependencies, dynamic boundaries, or obligations appear.

1. **Before each slice:** Establish a pre-edit baseline with relevant existing checks where practical. Reuse matching baseline evidence instead of repeating unchanged checks; report any baseline limitation. Separate pre-existing failures from failures introduced by the slice; preserve their output and precise remaining obligations. For a behavioral slice, specify the independent oracle and expected failure. Execute the discriminating check and confirm that it fails for the intended cause before implementation. An unrelated infrastructure failure is not the intended red. For a pure refactor, already-correct behavior, or nonbehavioral work, state why no new red is appropriate. Check the applicable preserved behavior. For historical work, report that a pre-edit red was not observed. Do not manufacture one by reversing accepted work.
2. **After each slice:** Execute checks that discriminate the changed behavior and affected integration. Inspect actual output, exit status, and which cases ran. Resolve causal failures and revise impact when new dependencies appear. Build success, mock behavior, and dispatch-only checks establish only their actual coverage.
3. **After test maintenance:** Check that the maintained tests still protect every surviving obligation. For test-infrastructure cleanup, first validate that the cleanup preserves the original checks before changing expectations. Before changing expectations in response to a failure, also check the infrastructure, fixtures, setup, and selection. Establish replacement protection before removing old protection for surviving obligations. Intentionally retired behavior can require removing obsolete assertions without replacement; document the retired obligation. Execute the maintained checks and inspect the cases that ran; do not accept a passing empty selection.
4. **Final settled result:** Recompute impact from the complete selected-baseline difference, including committed, staged, unstaged, and untracked work. Include hook and generated writes. Reconcile the inventory, protection decisions, and execution selection; deduplicate covered checks and widen uncertain coverage. Execute every required full/release check and preserve normal hooks and review gates. Reuse matching evidence only when implementation, inputs, configuration, environment, services, and actual coverage still match. A new session alone is not a reason to repeat checks.

## Record evidence and review

Keep compact notes of commands, actual results, covered obligations, failures, and evidence locations in every execution context. Keep failed results as history. A failure needs a causal fix or a precise remaining obligation; a passing command does not erase an unresolved obligation.

For a prepared change, use `purpose:"baseline"` for pre-edit observations and `purpose:"red"` for intended failures. These records are history, not final assurance. Use current verification evidence for settled checks. `scope` names exact files meaningfully covered. Optional `inputPaths` must conservatively include actual test files, transitive implementation, fixtures, and relevant configuration. Omit it for conservative whole-checkout freshness when the inputs are uncertain; do not narrow it to obtain a fresh result.

An eligible passing current check can name earlier evidence IDs in `supersedes` only when its scope covers their scopes and its assertions preserve their obligations. Supersession preserves the earlier records as history. Runtime coverage validation does not prove assertion strength. Use `verificationBasis` for check freshness and the current plan/review `basis` for review. Fresh evidence alone does not establish overall plan validity. Checkbox changes and result bookkeeping do not automatically invalidate application checks; substantive task changes still need reconciliation. Changed source, tests, relevant configuration, or authority invalidate corresponding assurance. Historical passes are not current passes.

For a settled prepared change or branch integration, obtain a real independent final reviewer through a native subagent or separate reviewer environment. For ordinary repository work, follow the applicable repository review gates. Supply each required reviewer with the actual target, complete baseline difference, contribution dispositions where applicable, test-change plan, executed results, and remaining limits. Ask for missing consumers, unsupported structure, invented justification, incomplete migration, counterexamples, and the strongest simpler alternative. Do not require another agent for every slice or invent attribution. Resolve findings and obtain required review of material corrections; refresh checks whose inputs changed.

For a prepared change, call `validatePlan` with `review:{basis,reviewer,examined,alternative,findings}` using the actual current basis. For ordinary work and branch integration, keep the actual review and findings in normal evidence notes and honor the completion gates for that context. Planning retains its artifact validation and human review frontier; it does not claim implementation completion.

Report protection decisions, commands and cases executed, and baseline and intended-red results or justified exceptions. Include final coverage, reused or superseded evidence, and independent review attribution. Identify unresolved failures, unexecuted checks, and remaining uncertainty. Keep the actual outcome compact and link evidence where available. Do not report inferred runtime or native behavior as observed behavior.

Completion: the required checks and review for the selected context support the settled result; otherwise report the precise obligations that prevent completion.
